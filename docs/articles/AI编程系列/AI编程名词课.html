01大模型：一台会预测下文的发动机

理解 AI 编程，得从模型会做什么、不会做什么说起。

大模型（LLM）是在海量文本上训练出来的概率模型，核心工作是根据已有内容预测后续 token。网页聊天框里的模型本身只负责生成内容：它看不见你的文件系统，改不了代码，也跑不了命令。所谓"编码模型"，通常是指在代码数据和编程任务上做过针对性训练或强化的模型。

模型也不是数据库。没有搜索、RAG 或其他工具时，它不能临时查证资料，只能根据训练中学到的模式和当前上下文生成答案。于是，一个不存在的函数名、一个根本没有的参数，也可能被它用很肯定的语气写出来，这就是常说的"幻觉"。生成和核实是两件事，所以 AI 产出必须经过测试、文档或人工复核。

快模型、慢模型和"思考档位"

快模型（非思考）

读完直接给答案。便宜、延迟低，适合代码补全、写单测、改小函数、解释代码这类一次到位的活。

慢模型（思考/推理）

先在内部"想"一段再回答，可以调思考强度（low / medium / high）。适合复杂重构、跨文件排查、架构问题——更准，但更贵更慢。

不少模型允许切换推理强度。小改动用低档，复杂排查再开高档，通常比所有任务都拉满更省钱。高档并不保证每次都更准，却几乎一定更慢、消耗更多 token。任务分级的方法见模型选型篇。

02Token 与上下文：它为什么会忘事

AI 干着干着开始跑偏，往往跟 token 和上下文有关。

Token是模型处理文本的最小单位，一段中文、一行代码、一个文件都会折算成若干 token。计费按它算，容量也按它算：同样的内容，代码比自然语言更"碎"，通常更费 token。

上下文窗口（context window）是模型单次处理内容的容量上限。你的提问、它读过的文件、命令输出和历史对话，都要占用这块空间。接近上限后，客户端会截断旧内容或压缩成摘要；细节一丢，表现出来就像"忘了前面说过什么"。窗口大小只是上限，不等于模型能同等准确地利用其中每一段信息，因此把整个仓库一次性塞进去通常不是好办法。

一个实用认知

AI 表现差，不一定是模型能力不够。相关文件没给、无关日志塞得太多，都会让答案跑偏。把任务目标、必要文件和真实命令结果交代清楚，通常比反复雕琢一句"神奇提示词"更有效，这就是上下文工程要解决的问题。

03三代形态：从副驾驶到司机

从补全到 Agent，变化不只是功能变多，人和 AI 的分工也变了。

代际形态人机分工
一代代码补全（2021～）你写主体，它在光标处猜下一行，按 Tab 接受。主语始终是你。
二代对话式助手（2022～）把报错和代码贴进聊天框问它。它看不见你的仓库，也跑不了你的测试，复制粘贴的搬运工还是你。
三代Agent 智能体（现在）你只说目标："给订单模块加退款功能，测试跑绿再叫我"，它自己读文件、改代码、跑测试、看报错、接着修，循环到完成。

补全和聊天助手主要给建议，执行动作仍由人完成；Agent 则能直接读写仓库、运行命令。权限一旦变大，关注点自然会从"怎么问"转到"能让它做什么，以及怎么验收"。

04Agent 与 Harness：体验差在模型外面

同一个模型放进不同客户端，体验可能差很多，差别主要在模型外面的那套系统。

光有模型还干不了活，它只有一张嘴。要让它替你动手，得给它配一整车：

眼睛

读文件、搜代码、看仓库结构的工具，让它"看得见"你的工程。

双手

改文件、执行 shell 命令、跑测试、操作 git 的工具调用。

记性与工作方法

上下文管理：任务长了会压缩摘要、维护项目记忆，不至于第三小时忘了第三分钟的目标。

刹车与规矩

权限控制：删文件、推送、改配置这类危险动作要先过你确认，敏感目录直接禁入。

术语卡：Agent 与 Harness

Agent = 大模型 + 工具 + 循环：模型不光会说，还能调工具，执行完看结果、再决定下一步，如此循环直到任务完成——读 → 改 → 跑 → 看报错 → 再改。跑这个循环的整套框架，行话叫 harness（字面是"马具"：马是模型，缰绳、马鞍就是 harness）。Claude Code、Cursor、Copilot 这些产品，本质都是 harness + 各家模型的组合。

许多客户端可以调用同一批模型，实际体验仍会不同。上下文怎么组织、工具怎么设计、权限怎么管、失败后怎么重试，都会影响任务能不能完成。选客户端时，模型只是其中一项，harness 的工程质量同样关键。

聊天机器人通常只给出参考代码，运行和纠错要靠人；Agent 可以在工具允许的范围内改代码、跑测试，再根据真实报错继续修。这个验证闭环能省掉来回复制粘贴的时间，也带来了新的风险：它真的会执行动作，因此权限和沙箱不能省。

05生态概念速查表

技术讨论里最常见的七个词，一张表就能跟上话题。

概念一句话解释为什么要懂
MCPAI 客户端接入外部系统的开放协议，可以理解为"USB-C 接口"决定 AI 能不能连你们的 Jira、CMDB、数据库、日志平台——接上之后它干的就不是"写通用代码"而是"干你们的活"
规则文件放仓库里的"给 AI 看的团队规范"（AGENTS.md 等）把构建命令、目录约定和禁改项写进仓库，减少团队成员反复口头交代
Skills / 插件把可复用的流程（如发版前检查）封装成 AI 随取随用的技能包把老员工的经验变成全团队可复用的资产
子代理（sub-agent）主 Agent 派出的专职小助手，干探索、写测试、做审查这类细分活复杂任务并行化，也防止主上下文被搜索结果塞爆
沙箱 / 权限模式限制 AI 只能读、还是能改文件、能不能执行命令、能不能联网企业安全的第一道闸门，选型必看
HooksAI 动作前后自动触发的脚本：改完文件自动跑 lint，提交前自动跑测试把质量门禁挂在 AI 动作上，不靠人盯
提示缓存重复发送的固定前缀（如规则文件）可被缓存大规模使用时显著降账单、提速度

再加两个偶尔出现的词：RAG 是"把公司资料检索出来喂给模型"，适合让 AI 查内部知识；微调 是"用公司数据再训练模型"，贵且更新慢，多数团队用不上，遇到再展开。

06AI 会不会取代程序员

与其争论会不会取代，不如看任务能否说清、能否验收、由谁担责。

  • 能被清晰描述、有验收标准的活，AI 已经能大量接管：样板代码、单测、脚本、日志埋点、接口对接、数据清洗、UI 还原、文档。
  • 依赖隐性知识、跨系统权衡、出事要担责的活，仍以人为主：架构决策、性能极限优化、线上事故定位、模糊需求澄清、资金与安全相关逻辑。
  • 责任不会转移：AI 可以写代码，但点合并按钮的是人。出了事故，责任属于提交并审查代码的人，这是行业共识，也已写进主流平台的产品规则（AI 代理署名的 PR 需要额外一次人工批准）。

AI 更像放大器，不是签字负责的人。代码库混乱、测试缺失时，它会更快地产生难审的改动；规范清楚、反馈及时，它才更容易稳定提效。上线工具前补齐基本流程，往往比买完席位再补治理省事。
