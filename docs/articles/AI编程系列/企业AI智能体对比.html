01先分类：企业里常见的四类"智能体"

产品名称可能相似，实际工作对象并不一样。按任务、产出和验收方式分类，选型才有可比性。

① 编程 Agent（Harness）

替你写代码：读仓库、改文件、跑测试、看报错、改到绿。产出代码与 PR。代表：Claude Code、Cursor、Copilot、ZCode、CodeBuddy 等（逐家对比见系列之四）。

② 企业知识智能体

站在公司知识上回答问题：检索内部文档后作答，产出答案、摘要、工单回复。代表：Dify、Coze（扣子）、RAGFlow 等平台上自建的问答应用，以及套件内建的知识助手。

③ 工作流自动化 Agent

替你跑流程、连系统：触发、编排、调 API、写工单、发通知。产出动作与流转。代表：Zapier、Make、n8n 及各类"Agent 化"的编排与 RPA 平台。

④ 办公智能体

长在你每天用的套件里：起草、总结、翻译、改格式。产出文档草稿与纪要。代表：M365 Copilot、Workspace 的 Gemini、WPS AI、飞书智能伙伴等。

这四类对应四种常见问题：编码和返工拖慢交付，资料散落导致重复答疑，跨系统流程靠人工搬运，日常时间被纪要和初稿占满。它们更像组合件，不是互相替代的四选一。企业未必需要一次配齐，应该先看瓶颈在哪里。这个分法与系列之四中"补全、Agent、审查 Bot 各管一段"的思路相同，只是把视角从研发团队拉到了全公司。

表里值得多看一眼的是"Agent loop 自主循环"。编程 Agent 通常拥有最完整的"执行—验证—修正"闭环，因为代码任务已有编译、测试和 CI 等反馈机制。其他类型也能做循环，但验证往往没这么直接，能放开的自主权自然不同。

03关键分界：有没有"确定性裁判"

四类产品为什么采用不同的交互和权限设计，关键在于任务有没有可靠的机器反馈。

术语卡：确定性裁判

这里指不依赖主观判断、可以重复执行的验证机制。编译器是否报错、测试是否通过、CI 是否放行，都是编程任务的裁判；流程系统的状态校验、幂等检查和回滚机制也能提供反馈。至于"答案是否完整""纪要是否准确"，机器可以辅助评分，却很难替代业务人员做最终判断。

裁判决定了两件事：

  1. 自主权能放多大。有可靠反馈的任务，Agent 做错后更容易被及时拦下并重试，因此编程 Agent 适合运行"读 → 改 → 验 → 再改"的循环。没有同等级反馈时，错误答案可能直接进入客服回复或管理决策，知识智能体就应停在建议和草稿环节。
  2. 治理怎么设计。系列之五强调"No change should land unread"，是让机器验证和人工判断各守一道关：测试、CI 负责可自动检查的部分，人负责需求是否满足、风险是否可接受。知识答案、文档和高风险流程动作缺少硬性裁判时，人工确认更不能省。

给选型者的一个判据

评估"智能体"产品时先问："它做对了，靠什么判定？"如果只能回答"让模型再检查一次"，就不该贸然放开高风险权限。编译、测试、状态校验、审批与回滚都算具体答案；验证机制越弱，人工确认越要靠前。

04常见错配与正确姿势

边界不清，预算和权限就容易配错。下面五种情况尤其常见。

常见错配后果正确姿势
拿知识智能体（Dify / Coze 应用）写代码没有代码工具、沙箱与验证循环，产出的是"参考代码"，搬运与验证还是人写代码走编程 Agent（系列之四）
拿编程 Agent 当知识库问制度、问规范没有权限分级的 RAG，答案靠上下文里塞多少算多少，还可能幻觉知识问答走知识智能体；编程 Agent 需要知识时，用 MCP 接知识库
在编排平台上自建编程 harness上下文工程、沙箱、验证循环全要自己造轮子，质量长期追不上成品平台管流程；写代码订阅成品 harness
让知识智能体"执行制度"（如自动审批）提示词不是门禁，答案也不担流程责任；错了没人拦制度执行挂确定性规则（审批流、hooks）；智能体只负责解释与起草
办公智能体全员铺开当"生产力革命"草稿质量参差，没有验收动作就没有可核算的收益圈定高频低风险场景（纪要、周报、初稿），配模板与验收动作

这些错配有个共同点：产品的执行能力和任务的验收方式没有对上。先明确产出由谁验、错了怎么撤，再决定买哪类工具、给多大权限。

05知识智能体专场：选型六问

知识智能体看起来最容易搭，长期效果却很依赖资料治理和运营，值得单独展开。

术语卡：RAG

把公司资料检索出来喂给模型，再让它作答，适合"让 AI 查内部知识"的场景（口径同名词课）。它的本质是给模型配一个"先查再说"的工作方法，缓解但不消灭幻觉。

  1. 别只盯模型。RAG 的切片、元数据、检索与重排会直接影响答案质量。上线前先处理重复文档、过期版本、目录和权限元数据；知识库本身混乱，换更贵的模型也很难稳定补救。
  2. 权限即合规。检索必须按人过滤到文档级：谁能问、能看到哪一档，跟着他在源系统的权限走。知识智能体最常见的事故不是模型胡说，而是权限过滤失效，智能体变成越权读档的通道（HR 文档、薪酬表、未公开材料被全员可检索）。上线前把"越权检索"列为专项测试。
  3. 答案必须带引用。无来源的答案不上线；引用可点开，人工抽检才有抓手。这也是知识智能体与"裸聊模型"的分水岭：能不能为答案指认出处。
  4. 拒答优于编造。"知识库里没有"就是正确答案。检索置信度低时拒答并转人工，比硬编一条像模像样的答案好得多，幻觉治理的优先级高于模型选型。
  5. 评测先于上线，抽检贯穿运营。用真实问题和标准答案建离线评测集，上线后持续抽检。除了满意度，还要看引用是否支持结论、人工纠正率和拒答准确性；语气讨喜不代表答案正确。
  6. 资产要能复用。把知识能力沉淀成 MCP server 之后，编程 Agent、工作流、办公助手都能消费同一份知识库。别让知识锁死在单一平台的应用格式里，这和系列之四的结论是同一条：模型留着换，资产要能带走。

安全侧补两条

知识智能体引入两类新攻击面：间接提示词注入（恶意内容藏在被检索的文档里，劫持智能体行为）与知识库投毒（污染源文档即污染所有答案）。这两类都在 OWASP LLM Top 10 的清单上；对外提供服务时，还要按对外 AI 产品的监管口径另做评估（见系列之五合规一节）。

06采购与落地：一页决策

先确认业务缺口，再看产品；顺序反过来，很容易为了工具找场景。

你缺的是该上哪类预算形态第一步
写代码的手：交付瓶颈在编码与返工编程 Agent席位订阅或按量（见系列之三、之四）选 1~2 个试点团队跑 90 天路线（见系列之五）
查资料的嘴：同一个问题答三遍、新人上手慢知识智能体平台自建一次 + 持续运营人力先治知识库与权限模型，再上问答（本篇第 05 节六问）
跑流程的腿：人力耗在跨系统搬运与人工触发工作流自动化按执行量 / 平台席位挑一条高频流程先做确定性编排，AI 决策点后加
写文档的手：时间泡在纪要、周报、初稿办公智能体随套件席位圈高频低风险场景，配模板与验收动作

两条横向提醒：

  • 数据边界按类分别评估。四类的敏感面完全不同（代码 / 知识全集 / 系统凭据 / 邮件文档），不要做一次"AI 出网评估"就全部放行，见总表"数据敏感面"一行。
  • 治理底线四类共用一套。人在回路、责任在人、默认不信任、可追溯，条款可以直接沿用系列之五；差别只在验证手段各配各的：编程配 CI 门禁，知识配评测抽检，流程配审批回滚，办公配人眼验收。

采购时别急着问"有多智能"，先问"产出怎么验收"。验收说不清，工具类别、权限边界和预算都很难定准。

07结论：四类是器官，不是替代品

把前面的分析收成三条可执行的判断。

  1. 四类各有分工，没有全能冠军。编程、知识、流程、办公解决的是不同瓶颈，选型从"缺什么"出发，不要从谁的宣传更响出发。
  2. 自主权跟着验证能力走。代码和流程有较强的自动反馈，可以在隔离环境里逐步放开；答案和文档更依赖业务判断，应把人工确认留在发布之前。看到"全自动"的宣传，先检查它的验证与回滚机制。
  3. 资产跟着协议走。MCP、SKILL.md、开放格式让四类共享同一批资产：同一个知识库、同一套规矩、同一批技能。优先选协议开放的那家，四类之间才不会出现四座数据孤岛。

验证做到哪，自主权就放到哪。机器能可靠检查的任务，可以在边界内让它多跑几步；检查不了的，仍应把 AI 放在建议席。
