01三条红线与六条原则

先把不能碰的边界写清楚，再发席位。红线宜少，执行宜硬。

三条红线（违反按安全事件处理）

  • 数据与凭据：密钥、客户数据、未公开信息，不贴给未审批的外部模型。判据简单，不愿发全员邮件的内容，不要贴给 AI。
  • 不碰生产：AI 会话不持生产写权限，危险命令必须被确定性规则硬拦，而不是靠人点确认。
  • 必须人审：AI 生成的 PR 必须由人评审，禁止自审自批。No change should land unread。

红线管住事故，日常判断可以靠下面六条：

  1. 人在回路：AI 可以写，必须由人审；任何环节不得"因为 AI 说可以就合并"。
  2. 责任在人：提交者就是责任人，事故复盘不许拿"AI 生成的"当免责理由。
  3. 默认不信任：AI 产出按外部来源代码的标准审查，评审、测试、扫描一样不少。
  4. 数据最小化：只给完成任务必需的信息，能脱敏就脱敏，能本地就本地。
  5. 能力分级授权：权限越大要求越严，默认只读或可改代码，不可碰生产。
  6. 可追溯：每个 AI 参与的变更，都能查到用的什么工具、什么模型、谁审的。

如果只做三件事

① 发布三级清单与三条红线（本篇第 02、03 节）；② 给每个仓库配规则文件与受管安全配置（第 05 节）；③ 每两周给工程师半天正式学习时间（第 06 节）。

02场景三级清单：绿灯 / 黄灯 / 红灯

绿灯直接用，黄灯加评审，红灯按安全事件处理。建议放进团队 Wiki 和新人手册，比口头提醒管用。

绿灯：鼓励自由使用（无需审批）

场景说明
代码补全、注释、命名IDE 内联补全，提效最直接
写单测、造测试数据（非真实客户数据）AI 强项，有测试兜底
文档、README、发布说明低风险高收益
解释陌生代码、读开源库、翻译报错学习加速器
脚本、正则、SQL 草稿（只读库）执行前人工复核
本地 / 测试环境的小范围重构有测试与 CI 保护
日志分析、问题定位假设结论由人验证

黄灯：可用，但走加强流程（评审 / 审批）

场景附加要求
生产业务逻辑代码逐行评审 + 单测覆盖率不低于基线 + CI 全绿
数据库 Schema 变更、迁移脚本DBA 审批；影子库先验证；必须有回滚脚本
认证、鉴权、加密、支付计费安全负责人参与评审；禁止 AI 生成密钥证书
依赖升级、新库引入SCA 白名单 + 许可证审查；不允许 AI 擅自引新依赖
IaC、CI/CD 流水线平台团队评审；非生产环境先验证
对外 API 契约变更契约测试 + 兼容性评审
性能敏感路径、核心算法要基准测试数据，不接受"AI 说这样更快"
批量修改（>10 文件或 >400 行）拆分提交、分批评审，拒绝"巨型 AI PR"

红灯：禁止，违反按安全事件处理

禁止项原因
密钥、Token、证书、私钥贴进 AI 对话凭据直接泄露，可能已在外部留存
客户数据、个人信息贴给未审批的外部模型违反《个人信息保护法》与合同义务
未公开财务、并购、核心算法交给外部模型商业秘密风险
用个人账号 / 未审批工具上传公司代码出境不可控、无审计
AI 直接操作生产（改配置、删数据、发版）不可逆事故
AI 代码未经审查提交主干或发布责任链断裂
生成规避授权、破解、爬虫绕过类代码法律与合规风险
把未获授权的渗透测试 / 漏洞利用请求交给通用模型超出厂商使用政策与法律授权范围，可能触发封号与法律风险

03数据与安全防线

数据一旦贴出去就很难收回。防线应放在账号、目录、出网和命令拦截上，不要指望模型自己守规矩。

数据与密钥红线的落地清单

  1. 统一用公司审批的企业账号，禁止个人订阅处理公司代码。
  2. 仓库不得出现明文密钥；.env、secrets/、证书同时进 .gitignore 和 AI 忽略配置（.cursorignore 等）。
  3. 配置 AI 的禁读清单：财务、法务、HR、密钥、生产配置目录一律拒读，多数客户端默认允许读这些路径，必须显式关掉。
  4. 敏感项目能内网就内网。
  5. 供应商条款先审："不用于训练""最短留存""不跨境"写进合同。注意免费档与商业档的数据用途可能不同（如 Amazon Q Free 档可用于训练、Pro 档排除），白名单要写到"档位"。
  6. 必须外发时先脱敏：用结构等价的假数据。
  7. 审计日志先确认能查到什么、留多久，Copilot 企业日志 180 天且不含本地会话，Claude 默认不记提示词正文（API 数据留存 30 天与"审计能否取回提示词正文"是两回事），想当然会到取证时空手而归。日志建议流式接入 SIEM。
  8. 离职转岗即时回收许可与 API Key，纳入资产清单。

最重要的一条：防线放在环境层

三个实测数字决定了这个判断：用户对权限弹窗的批准率 93%，靠人点确认等于没拦；OS 级沙箱上线后权限弹窗减少 84%，环境隔离能替代大部分"人肉确认"；钓鱼诱导 AI 外发凭据的实验 25 次成功 24 次，意图判断拦不住，物理隔离才拦得住。落地五件事：

  1. 凭据与敏感目录显式拒读（.env、secrets/**、~/.ssh、~/.aws/credentials）；
  2. 出网白名单：只放行必需域名；
  3. 危险动作硬拦：删除、强推、生产库操作用确定性规则（hooks）拦截；
  4. 受管配置下发：用企业级受管设置强制覆盖用户本地配置，锁定权限规则、MCP 白名单、模型清单；
  5. CI 硬门禁：AI 生成的 PR 必过 SAST、依赖扫描、secret scanning 三件套。

工具与模型治理（企业级）

  • 统一网关：所有 AI 请求经网关转发，统一鉴权、限流、计费、日志与模型白名单；
  • 工具白名单：明确允许的客户端清单，新工具评审后准入；
  • 模型分级：按项目敏感级定义可用档位，高敏项目只允许私有化或零留存条款的模型；
  • MCP 白名单：厂商不做第三方 MCP server 的安全审计，"接入审核"不等于"数据可信"，接入前自行评估数据访问范围；
  • 会话可见性：部分产品的云会话默认对"有仓库可见权限的人"开放，私有仓库要收紧；
  • 规则与提示词版本化：规则文件与 prompt 库走版本控制与 PR 评审；
  • 应急预案：核心流程至少备两条可替换通道（如"海外旗舰 + 国产旗舰"），每季度演练一次切换，明确降级预案，2026 年出现过顶级模型因管制被临时下架的先例。

供应商条款必查项（采购前逐条确认）

检查项要问的问题已知的差异
训练用途我的代码会进训练集吗？商业版通常"不训练"，免费档常有例外
留存期数据留多久？能否零留存？Anthropic 商业版 30 天；零留存需单独启用且会禁用部分功能
审计能力能拿到什么日志？GitHub 180 天不含会话；Anthropic 不记提示词正文
IP 责任生成代码侵权谁担责？微软对 M365 Copilot 有条件赔偿；GitHub 明示用户自担，不得默认厂商兜底
公共代码匹配能阻止与公开代码雷同的建议吗？GitHub 付费档均可开启，应作为默认

04评审、度量与合规

写在 Wiki 里的规范容易被跳过。门禁要挂到 PR 和 CI 上，度量盯交付和质量，合规把日志留住。

评审与质量门禁

  1. AI 不能自审：AI 写的代码必须人类评审，Bot 只能当补充；仓库都要有 CODEOWNERS 与分支保护，AI 生成的 PR 同样需要至少一名人类 Approver。主流厂商已把"代理不得自批"做成产品默认。
  2. 测试不达标不合并：新增/修改逻辑必须有对应测试，明确覆盖率门槛。
  3. 大改必须拆分：单 PR 有效改动建议 ≤400 行，AI 一次生成上千行的一律要求拆分。
  4. 规则挂到动作上：规则文件是建议性的，hooks 是确定性的，能自动拦的不要靠文档提醒。

No change should land unread，没有人读过的改动不允许合入。建议把这句直接写进公司规范当总原则。

评审 AI 代码时优先看六处：边界与异常（空值、并发、时区、幂等）；安全（注入、越权、SSRF、日志泄密）；资源释放与循环内 IO；是否引入未审批依赖；兼容与回滚路径；以及"看起来太顺"的部分：AI 最容易在看不出问题的地方编造接口、漏掉错误处理。

度量：证明有效，并防"唯指标"

层次指标说明
过程周活跃率、补全采纳率、AI 参与 PR 占比衡量普及；采纳率行业常见区间 20%~35%
结果PR 前置时间、部署频率、需求吞吐DORA 五指标为主，看"变快还是变慢"
质量变更失败率、回滚率、缺陷密度、返工工时、评审时长AI 提效常伴随这些指标恶化，单独盯
成本人均 token 成本、单 PR 成本与提效折算 ROI

严禁用"AI 代码行数 / AI 代码占比"做考核

它同时激励两种坏行为：生成冗余代码，以及把现有代码让 AI 重写一遍。这个指标业界也没有统一定义，各家口径不能互比。考核绑定交付结果与质量；DORA 官方建议用"单次被采纳变更的成本"与"返工率"替代输出量。

合规要点（请法务复核后定稿）

  • 内部自用不属于《生成式人工智能服务管理暂行办法》的管辖范围（第二条：仅研发应用、未向公众提供服务不适用），但个人信息与商业秘密红线不变。反过来，把 AI 做进对外产品功能则要按算法备案与安全评估口径另议。
  • 对外交付物里的 AI 生成内容按《人工智能生成合成内容标识办法》（2025-09 施行）处理：显式 + 隐式标识，日志留存不少于 6 个月。
  • 数据出境：年度累计出境 100 万人以上个人信息（或 1 万人以上敏感信息）需申报安全评估，评估有效期 3 年。往海外模型贴一段含手机号的日志，也算数。
  • EU AI Act（面向欧盟市场时）：内部编程工具不在高风险清单；透明度义务 2026-08 起适用。
  • 安全扫描对齐 OWASP：供应链失效（A03:2025）对应 AI 引入的依赖风险；自建 AI 应用注意提示词注入（LLM Top 10 首位）。

05实操指南：装好、用好、别踩坑

客户端界面各不相同，下面这些动作大多通用。

第一天 checklist

步骤要点
1. 企业账号登录不用个人账号，确认 SSO 与团队席位
2. 配模型与网关指向公司统一网关，确认档位与限额
3. 配忽略清单密钥、客户数据、大二进制、构建产物对 AI 不可见
4. 选权限模式起步用"只读探索 / 每步确认"，熟练后再放宽
5. 添加规则文件仓库根目录放 AGENTS.md，这是最高杠杆动作，模板见附录 A
6. 跑通小任务让它修一个带测试的简单 bug，观察它怎么读文件、怎么验证
7. 装质量钩子提交前自动 lint / format / 单测，让改动立刻有反馈

规则文件：把团队规范翻译给 AI

在仓库根目录放一个规则文件，每次会话自动进上下文，等价于每次都给 AI 做一遍新人培训。写法三个要点：短而具体（100~200 行，越长越被忽略）；写"怎么做"（命令、目录、约定），不写"要努力"这类空话；覆盖技术栈版本、目录职责、构建测试命令、代码风格、禁止事项、提交信息格式。模板见附录 A。

进阶：规则长成流程，就封装成 Skill

规则文件解决"每次都在场"的项目约定；当某套规则长成固定流程——新仓库接入团队规范、发版前检查、事故复盘——更好的载体是 Skill（SKILL.md 开放格式，放仓库里按需加载）：AI 只在对应场景把它调进上下文，平时不占窗口。典型做法是 setup 类 skill（如 /setup-skills）：在新仓库跑一次，自动生成规则文件与配套约定，把"老带新"的口头交接变成全团队可复用的资产。规则文件管常态，Skill 管流程，两层配合。

上下文管理：决定效果的第一因素

做法说明
先探索，再动手让它先读代码给计划，确认后再改，用好 Plan 模式
给对文件明确 @ 相关文件，比让它全仓乱搜更快更准
换任务换会话长会话污染上下文，及时 /clear 或新开
小步快跑一次一件事，改完立刻验证提交，不要"一把梭重写模块"
让它自己验证要求跑测试并贴出结果，不接受"我看应该没问题"
压缩与交接大任务先写方案文档，新会话按文档执行
善用子代理探索、审查这类"读得多说得少"的活交给子代理，别塞满主上下文

日常五类高价值用法（按 ROI 排序）

  1. 写测试：补单测、补边界用例、造测试数据。风险最低收益最直接。
  2. 读代码 / 接手遗留系统：解释调用链、画流程、列出"改这里会影响谁"。
  3. 修 bug：给报错栈 + 复现步骤 + 相关文件，要求"先给根因假设再改"。
  4. 样板与重复劳动：CRUD、DTO、日志埋点、配置迁移、批量改名。
  5. 审查辅助：让 AI 以挑刺角色审 diff，结论由人判断。

要谨慎的用法：让 AI 设计核心架构、"顺手重构"你不熟悉的模块、直接生成大规模迁移脚本跑生产、读完成仓后"整体优化"。这四类要么收益为负，要么属于红灯。

三种典型工作流

A. 交互式（人在旁边，最常见）：

明确任务与验收标准 → 让它给计划 → 确认/修正计划 → 小步实现
→ 跑测试与构建 → 人工复查 diff → 写清 PR 描述 → 提交

B. 异步 / 云端（任务放出去，回头收 PR）：

把任务描述（含约束、验收标准、禁改文件）交给云端 Agent
→ 它产出 PR → 人在本地验证 → 补齐测试与文档 → 合并

适用机械性改造、依赖升级、批量修 lint；必须配沙箱、只读权限、CI 门禁、人工终审。

C. 编排式（复杂任务拆多代理并行）：

主代理拆解任务 → 子代理并行（探索 / 实现 / 测试 / 审查）
→ 主代理汇总 → 人审最终产出 → 合并

适用大型迁移、全仓审计；成本与风险同步放大，先试点再推广。

十个常见反模式

反模式后果正确做法
上下文塞满无关文件关键信息被淹没，答非所问精准 @ 文件 + 换新会话
"帮我优化一下这个项目"大范围无意义改动限定范围与验收标准
不看 diff 直接提交混入后门、调试代码、密钥强制看 diff，写进规范
让它"保证没问题"得到的是语气，不是证据要求跑测试并贴输出
用它替代理解团队能力退化，事故时无人能修AI 解释 + 人复述验收
长会话一路用到底质量随上下文膨胀下降任务切换就清空
忽略 AI 新增的依赖供应链风险依赖变更必须过 SCA 白名单
让 AI 直接连生产库不可逆事故只读副本 / mock
无测试的"能跑就行"回归缺陷先写测试再实现（TDD 很适合 AI）
只靠 AI 审查 AI盲区叠加人类 Approver 不可省

经验沉淀

把各仓库的规则文件、好用的提示词、hook 脚本集中到一个内部仓库持续迭代；每个团队配 1~2 个"冠军"负责答疑和收案例；建一个案例库，"做得好的 20 个、翻车的 20 个"。翻车案例比成功案例值钱，它是红线清单最真实的来源。

0690 天落地路线：成本与推广

先在一两个团队打样，用真实数据和翻车案例扩面，再写成制度。不要第一天就全员发席位。

阶段一 · 第 1~30 天
准备与试点
  • 成立虚拟小组，选 1~2 个代码库健康、有测试、业务压力大的试点团队
  • 搭统一网关、账号与审计

成本模型

AI 编程成本 = 席位订阅 + 模型 token 费 + 网关平台费 + 培训推广 + 返工与审查。各家订阅价格与用量口径见系列之四《客户端选型指南》第 08 节；这里只补三条本篇独有的账：

  • 厂商公开的用量参考大约是 $13 / 开发者 / 活跃日、$150~250 / 人 / 月，约 90% 的开发者低于 $30/活跃日。Agent 团队的 token 消耗可以到普通会话的数倍，账单要按任务类型分开看。
  • 失控真实发生过：Uber 四个月花光全年 AI 预算后限流；微软设用量上限；Shopify 给 agent 上"断路器"。所以云端 Agent 必配四道闸：单任务最长时长、最大 token、最大并发、单日花费上限，再按团队归因、月度复盘。
  • 省钱的常见做法：任务分级选模型（见系列之三）；打开提示缓存，把规则文件放在固定前缀位置；控制上下文长度，别整仓塞进对话；给云端 Agent 设上限；月底把"单 PR 成本"和交付结果放一起看。

推广机制：被验证有效的做法

冠军机制，每人每周 40 分钟：15 分钟在团队频道分享一条"这周我用 AI 干了什么/踩了什么坑"；20 分钟答疑、帮同事跑通第一次；5 分钟拉一个新人上手。30 天剧本：第 1 周建频道、第 2 周开始每周 show-and-tell、第 3 周结对、第 4 周交棒第二位冠军，避免单点依赖。红线：安全与合规问题一律转交管理员，冠军不得即兴作答。

给时间：每两周固定半天"AI 工程时间"，用来学工具、改规则文件、写案例，并计入正常工时。业余自学很难铺开。DORA 的生成式 AI 报告里，工作时间内提供专门学习时间，与团队采用度 +131% 相关。

用真实任务验收。试点结束时每人交一个 AI 显著参与的 PR，再交一个翻车案例。翻车记录往往更能暴露红线该写什么。

头一两个季度，审查和验证成本可能先上去，交付稳定性也可能变差。立项时写清楚：第一季度看采纳率和使用质量，第二季度再看吞吐与稳定性，避免刚好在最难看的时候被叫停。DORA 还观察到，清晰的 AI 使用政策与采用度 +451% 相关；这是关联结果，不是保证每个团队都能复制同一幅度。

附录 A：仓库规则文件模板（AGENTS.md / CLAUDE.md）

# 项目说明（给 AI 助手的规则文件）

## 项目概况
- 业务：一句话说明本仓库做什么
- 技术栈：语言/版本、框架、数据库、构建工具
- 目录结构：cmd/（入口）、pkg/（业务）、internal/（内部库）、scripts/（脚本）、docs/

## 常用命令（必须使用这些命令验证改动）
- 安装依赖：`make bootstrap`
- 构建：`make build`
- 单元测试（单个文件）：`go test ./pkg/foo/... -run TestName`
- 全量测试：`make test`
- 静态检查：`make lint`
- 本地启动：`make run`

## 代码约定
- 错误必须显式处理，禁止忽略 error
- 对外接口必须有注释与示例；内部函数保持短小（< 50 行）
- 禁止引入新依赖，除非在 PR 说明中获批
- 日志禁止打印手机号、身份证、Token 等敏感字段
- 时间统一 UTC 存储，展示层转换

## 提交与 PR 要求
- 提交信息：`type(scope): 简述`（feat/fix/refactor/test/docs/chore）
- PR 描述写明：改动原因、影响范围、验证方式、回滚方式
- 单 PR 有效改动 ≤ 400 行；大改必须拆分

## 禁止事项（红线）
- 禁止在代码、注释、日志、测试数据中出现真实密钥与客户数据
- 禁止修改 deploy/ 与 migrations/ 目录，除非任务明确要求
- 禁止执行 rm -rf、DROP、git push --force 等破坏性命令
- 禁止自动提交：所有提交必须人工确认

## 工作方式
- 修改前：先读相关文件并给出计划，等我确认
- 修改后：运行受影响范围的最小测试集并贴出结果
- 不确定时：明确说出不确定，不要猜接口名

附录 C：代码评审 Checklist（人审 AI 产出通用）

  1. 需求对齐：改动真的解决了问题吗？有没有做多余的事？
  2. 正确性：边界、异常、并发、幂等、时区、精度。
  3. 安全性：输入校验、权限判断、注入、敏感数据、依赖风险。
  4. 可维护性：命名、抽象层级、重复代码、注释是否解释"为什么"。
  5. 测试：覆盖失败路径了吗？是不是只测 happy path？
  6. 可观测性：日志、指标、追踪够定位线上问题吗？
  7. 性能：N+1、全表扫描、循环内 IO、无上限缓存。
  8. 兼容与迁移：老数据、老客户端、灰度与回滚。
  9. 干净的 diff：混入格式化/重排噪声了吗？
  10. 责任确认：我愿意为这段代码的线上表现负责吗？

附录 D：常见问题 FAQ

AI 写的代码出事故，责任算谁的？ 算提交与审批的人。AI 不是责任主体，也永远不会是。

可以让 AI 提交代码吗？ 可以生成本地提交，但推送、合并、发布必须由人触发，PR 必须有人类 Approver。

用 AI 会不会让绩效被质疑"产出不是自己写的"？ 考核看交付结果与质量，不看敲了多少字。"会用 AI 把事做成"就是当前的核心能力。

为什么不干脆全禁外部模型？ 私有化模型能力通常落后旗舰 6~12 个月且运维贵。合理做法是按敏感级分层：高敏走私有化，普通业务走企业版云端加零留存条款。

AI 老不按规范写，怎么办？ 九成是规则文件没写清或没进上下文。先写进仓库规则文件并验证生效，再考虑换工具。

需要给每人都买最贵旗舰吗？ 不需要。任务分级：日常补全小改用快档，疑难攻坚才上旗舰，配统一网关限额（见系列之三）。

能用 AI 刷测试覆盖率吗？ 能写测试，但不允许"为覆盖率的空测试"——断言要测真实行为，检查"断言恒真"的情况。

外包 / 合作伙伴能用我们的 AI 工具吗？ 默认不允许。确需使用时单独签数据条款、限仓库范围、开全量审计，由我方人员终审。
