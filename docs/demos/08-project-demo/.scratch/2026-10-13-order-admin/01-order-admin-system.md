# 订单管理系统（订单 CRUD + 汇总看板）

Type: prd
Status: ready-for-agent

## Problem Statement

用户目前没有任何可运行的订单管理工具。需要一个简单、完整、前后端具备的订单管理系统：能录入、查询、修改、删除订单，并通过一个汇总页面总览订单量、金额与状态分布。技术基线为 Java 8 字节码后端 + React 18 前端 + MySQL 8 存储，且最终能以单 jar 启动交付。

## Solution

一个单仓库、前后端分离开发、单 jar 交付的订单管理系统：

- **订单管理页**：分页列表（支持订单号/客户名称前缀搜索与状态精确筛选）、新建/编辑（弹窗表单）、删除（确认后逻辑删除）。
- **汇总看板页**：KPI 统计卡片（总订单数、总金额、待支付数、已完成数）+ 按状态分布饼图 + 近 7 天下单趋势柱状图。
- **后端**：Spring Boot 2.7.18 + MyBatis-Plus 提供 REST API，Flyway 管理建表迁移，统一 `Result<T>` 响应包装。
- **前端**：Vite + React 18 + TypeScript + Ant Design 5 + ECharts。

## User Stories

1. 作为管理员，我希望创建订单（填写客户名称、商品名称、数量、单价、状态、备注），以便订单被录入系统
2. 作为管理员，我希望订单号由系统自动生成，以便无需人工编号且保证唯一
3. 作为管理员，我希望分页浏览订单列表，以便订单多的时候也能顺畅查看
4. 作为管理员，我希望按订单号或客户名称前缀搜索、按状态精确筛选，以便快速定位目标订单
5. 作为管理员，我希望修改订单信息与订单状态，以便订单变化得以及时反映
6. 作为管理员，我希望修改状态时在五个状态中自由选择，以便操作简单直接、无需理解流转规则
7. 作为管理员，我希望删除订单前弹出确认提示，以便不会误删
8. 作为管理员，我希望被删除的订单不再出现在列表与统计中，以便数据保持整洁（逻辑删除）
9. 作为管理员，我希望总金额由系统按数量×单价自动计算，以便避免手工计算错误
10. 作为管理员，我希望在汇总页看到总订单数、总金额、待支付数、已完成数的统计卡片，以便一眼掌握全局
11. 作为管理员，我希望看到按状态分布的订单数饼图，以便了解订单状态构成
12. 作为管理员，我希望看到近 7 天每日订单数与金额的趋势柱状图，以便感知近期业务动态
13. 作为管理员，我希望用一条 `java -jar` 命令启动完整系统，以便部署演示足够简单
14. 作为开发者，我希望数据库表结构变更由 Flyway 版本化迁移管理，以便环境重建可追溯、可重复

## Implementation Decisions

- 单仓库布局：`backend/`（Spring Boot）+ `frontend/`（Vite）；开发期前后端分离运行，Vite dev server 将 `/api` 代理到后端 8080 端口。
- 交付形态：前端构建产物嵌入 Spring Boot jar 静态资源，同源提供服务，单 jar 启动；因此无需 CORS 配置。后端将非 `/api` 的未知路径回退到 `index.html`（SPA fallback），保证前端深链接/刷新在 jar 内可用。
- 数据模型：单表 `t_order`（不做订单明细子表）。字段：订单号、客户名称、商品名称、数量、单价、总金额、状态、备注；遵循仓库数据库规范——`id`/`create_time`/`update_time` 必备三字段、`is_deleted` 逻辑删除。
- 订单号生成规则：`ORD` + `yyyyMMddHHmmss` + 3 位随机数字，由后端在创建时生成；`order_no` 列建唯一索引 `uk_order_no` 兜底唯一性。
- 订单状态：`PENDING`（待支付）、`PAID`（已支付）、`SHIPPED`（已发货）、`COMPLETED`（已完成）、`CANCELLED`（已取消），创建与编辑时自由切换，后端不做流转合法性校验。
- 金额：`BigDecimal` 存储，单价/总金额均为 `DECIMAL(10,2)`，计算 HALF_UP 舍入保留 2 位小数，币种默认人民币（不设币种字段）；总金额 = 数量 × 单价，由后端计算，不信任前端传入。
- 分页与排序：默认页大小 10（前端可选 10/20/50），列表默认按 `create_time` 降序。
- API 契约（REST + 统一 `Result<T>` 包装）：
  - 订单 CRUD：创建、分页查询（带订单号/客户名称前缀匹配 `kw%`、状态精确筛选条件）、按 id 修改、按 id 删除（逻辑删除）。搜索口径遵循仓库数据库规范 1.2【强制】（严禁左模糊/全模糊）。
  - 汇总统计：KPI 聚合（总数/总金额/待支付/已完成）、按状态分组计数、近 7 天按日聚合（订单数、金额）。近 7 天口径：服务器本地时区，窗口为 [今日−6 天 00:00, 今日 23:59:59] 共 7 个自然日（含今日），按 `create_time` 的日历日分组，无订单的日期补零返回。
- 后端栈：Spring Boot 2.7.18 + MyBatis-Plus（分页插件），产出 Java 8 字节码（构建机 jdk17 + maven3，`maven.compiler.release=8`）；分层取仓库 Java 规范推荐分层的子集：Web（Controller）/ Service / DAO（Mapper），省略 Manager 层（单表演示系统无跨复杂度编排需求）。
- 数据库：MySQL 8 由仓库自带 `docker-compose.yml` 提供（`mysql:8`，宿主端口 3307 防与既有实例冲突，初始化脚本预建 `order_db` 与 `order_db_test` 两个 schema）；若用户本机另有 MySQL 8 实例，仅需修改 git 忽略的 `application-local.yml` 中的 JDBC URL 指向。Flyway 管理迁移脚本（Boot 2.7.18 托管 Flyway 8.5，需显式引入 `flyway-mysql` 模块）。
- 数据库凭据：经环境变量/启动参数注入为默认方式；本地开发允许明文写入 git 忽略的 `application-local.yml`（演示级豁免 Java 规范第 5 节【强制】"配置密码加密"，豁免理由：本地演示 + 文件不入库，见 Further Notes）。
- 前端栈：Vite + React 18 + TypeScript + Ant Design 5 + ECharts + axios；两个路由页面（订单管理、汇总看板）+ 顶部导航。
- 无认证、无权限体系（演示级系统）。

## Testing Decisions

- 好的测试只验证外部行为（HTTP 接口的输入输出、数据库最终状态），不测实现细节。
- 测试接缝：REST API 层（Spring Boot MockMvc + 随应用上下文加载的 MyBatis-Plus），是本系统唯一主接缝——测试使用 MySQL 实例的 `order_db_test` schema（compose 初始化脚本预建），由 Flyway migrate 建表、每轮测试前 clean+migrate 重置，覆盖：创建/分页搜索/修改/逻辑删除、总金额后端计算与精度、订单号唯一性、五个状态统计口径、近 7 天聚合口径（含窗口边界与补零）、已删除订单从列表与全部统计（KPI/饼图/趋势）中排除。
- 前端不加单元测试（演示级）；核心页面行为以手工/浏览器走查验收。
- Prior art：本仓库为空仓，无先例测试；本 PRD 建立项目首批测试。

## Out of Scope

- 认证、授权、多租户
- 订单明细子表（一单多商品）、库存、支付集成
- 严格订单状态机校验
- 消息通知、报表导出
- CI/CD 流水线
- 历史数据迁移
