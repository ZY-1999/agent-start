# 领域文档（Domain Docs）

SDD skills 探索代码库时应如何消费本仓库的领域文档。

## 探索前先读这些

- 仓库根的 **`CONTEXT.md`**，或
- 仓库根的 **`CONTEXT-MAP.md`**（若存在）——它指向每个上下文各自的 `CONTEXT.md`，把与当前主题相关的都读一遍。
- **`docs/adr/`**——读与即将改动的区域相关的 ADR。多上下文仓库还要看 `src/<context>/docs/adr/` 里上下文级决策。

这些文件不存在就**静默继续**。不要提示缺失，也不要主动建议先创建。`/domain-modeling` 技能（经 `/grill-with-docs` 触达）会在术语或决策真正定下来时按需惰性创建。

## 文件结构

单上下文仓库（本仓库采用）：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

## 使用词汇表里的术语

当你的输出要命名某个领域概念（issue 标题、重构提案、假设、用例名），使用 `CONTEXT.md` 里定义的术语。不要漂移到词汇表明确回避的同义词。

如果需要的概念还不在词汇表里，这本身是个信号——要么你在发明项目不用的说法（重新考虑），要么确实存在缺口（记下来交给 `/domain-modeling`）。

## 标出 ADR 冲突

如果输出与既有 ADR 矛盾，明确摆出来，不要静默覆盖：

> _与 ADR-0007（事件溯源订单）冲突——但值得重开讨论，因为…_
