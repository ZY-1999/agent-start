## 一、业务含义解释

这是一个 **B2C 商城的应付金额计算器**，规则如下：

| 参数 | 推断含义 |
|------|----------|
| `p` | 商品单价（元） |
| `t` | 购买数量 |
| `f` | 会员标记（结合你提供的背景；也可能是"首单标记"，建议查当时的 PRD） |
| `d` | 促销判定日期，`null` 表示不参与促销 |

计算流程：

1. **阶梯折扣**：数量 > 100 打 9 折；数量 > 50（且 ≤ 100）打 95 折
2. **会员折扣**：标记为 true 再乘 93 折
3. **促销月折扣**：指定月份再乘 8 折
4. **满减**：应付 > 999 元立减 50
5. 输出应付总额

## 二、发现的 Bug 与风险（按严重度）

### 🔴 1. `d.getMonth() == 5` 实际判断的是六月，不是五月

`java.util.Date.getMonth()` 返回 **0-based** 月份：一月是 0，六月是 5。

- 如果业务规则是"六月年中大促"——代码碰巧正确
- 如果业务规则是"五一促销（五月）"——**这个 bug 已经潜伏了十几年**，每年五月不生效、六月错误生效

**验证方法**：翻当年促销活动记录，对比六月/五月的订单折扣率。

**修复**（保持行为不变的前提下）：

```java
// 迁移到新 API（1-based），5 表示五月
if (d != null && d.toInstant().atZone(ZoneId.systemDefault()).getMonthValue() == 5) {
```

### 🔴 2. `double` 计算金额

单价 × 数量 × 折扣的浮点运算会产生精度误差（`0.1 + 0.2 != 0.3` 问题）。金额应使用 `BigDecimal`，历史脏数据需要核对。

### 🟡 3. 折扣可无上限叠加

数量折扣 + 会员 + 促销月三重叠加后，折扣系数最低可到 `1 - 0.1 - 0.07 - 0.2 = 0.63`，再叠加满减。若当年没有风控审核，存在被刷单的可能——建议查一下历史订单中折扣系数 < 0.7 的单子。

### 🟡 4. 使用已废弃 API

`Date.getMonth()` 自 JDK 1.1 废弃。如果项目正在做 JDK 升级（见 Demo 03），此类代码是重点改造对象。

### 🟡 5. 缺少参数校验

`t <= 0`、`p < 0`、`p` 为 `NaN` 时行为未定义：`calc(100, 0, false, null)` 返回 0，`calc(-1, 10, ...)` 返回负数。
