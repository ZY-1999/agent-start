# 测试流程编排

在缺产品经理、需求模糊、工期紧的交付环境里，测试不是"等文档到了再写用例"。这个 skill 决定**现在该做哪一阶段**，并把活交给对应的 skill。

四阶段对应交付链上四个真实卡点，不是流程装饰：

| 阶段 | 卡点 | 交给 |
| :--- | :--- | :--- |
| 一、澄清 | 需求有断层，开发按各自理解写 | `/qa-clarify` |
| 二、用例 | 开发内测不知道测什么，跑了等于没跑 | `/qa-cases` |
| 三、回归 | 修完不知道影响面，漏测复发 | `/qa-regress` |
| 四、收口 | 验收/演示前说不清版本到底能不能上 | `/qa-review` |

## 1. 定阶段

从用户这句话里找**最强的那个信号**，不要一次排完四个阶段：

- 拿到需求（PRD / 口头 / Confluence 页 / 截图），还没人写出"到底验什么" → **一**
- 要转测了，开发要做内测，需要一个最低门槛 → **二（L1 冒烟）**
- 需求已清楚，要成体系的业务流程用例 → **二（L2 场景，复杂时加 L3 功能）**
- 要验"谁能看到哪条数据"、角色隔离、越权 → **二（L2/L3 权限场景，不是专项）**
- 明确要做性能 / 安全 / 兼容性专项或要出报告 → **二（L4，默认不出）**
- Bug 修完了，开发提交了修复说明 → **三**
- 测试尾声 / 要验收 / 要给领导演示 / 版本已发布 → **四**
- 用户只说"要测了"，没给更多 → 默认从**一**开始，并说明为什么

**先判走哪条入口**：需求要留档、跨迭代、多人接手时，把澄清后的断言升级成 PRD（`/to-prd` 或 `/idea-to-prd` → `/to-spec`）；口头需求加工期紧时，断言直接进用例，别为了"规范"补一份没人看的 PRD；需求简单且完整、已被 `/to-spec` 的 completeness-bar 放行时，用例直接拿 spec 的验收标准，但**那道 gate 要复核一遍**——它判的是"够不够拆 spec"，不是"业务上没洞"。三条入口的取舍见 [`references/pipeline-map.md`](references/pipeline-map.md)。

停在选定的阶段。用户没要后续阶段，就不要预告后面四步怎么做——那会让他跳过眼前这步。

**完成标准**：说清本次做哪一阶段、为什么是这一阶段、产出物是什么。

## 2. 先看项目里已有什么

进入任何阶段前，读一次项目测试资产的布局，别让用户重复讲已经沉淀过的东西：

1. 找 `docs/qa/`（布局见 `references/project-layout.md`）：`glossary.md` 术语表、`knowledge/` 业务知识库、`cases/` 用例库。
2. 没有 `docs/qa/`，就问一次用户的资产放在哪（本地目录、Confluence 空间、禅道产品），按 `references/project-layout.md` 的路径登记写进项目 `AGENTS.md` 再继续。
3. 术语表存在时，后续所有产出必须用表里的词；表里没有的新词，产出后补回术语表。

**完成标准**：明确知道术语表、知识库、用例库三者的位置——存在则已读，不存在则已记录待建。

## 3. 交接

把活交给阶段对应的 skill，并带上三样东西：**模块名、需求来源、已有资产位置**。阶段交接时不要重新访谈一遍——上游已经问过的不再问。

需要跨系统取数或落数时，走已有能力，不要自己编：

- 需求在 Confluence → `confluence` skill 拉页面
- 需求在禅道 story → `zentao-cli` 读需求单正文与变更记录
- Bug 在禅道 → `zentao-cli` 查详情、提交验证结论

### 什么时候该离开 qa 桶

测试这条线有五处要借通用 skill，别自己重造。**能用 qa 桶解决的不要外借**——外借的代价是上下文切换和产出物格式不一致。

| 情形 | 借谁 | 带过去什么 |
| :--- | :--- | :--- |
| 需求方或研发就在对话里，能让半句话当场补全 | `/grill-me`；要留 ADR / 领域术语用 `/grill-with-docs` | 现有理解 + 待定点清单 |
| 需求要留档、跨迭代、多人接手 | `/to-prd` 或 `/idea-to-prd` → `/to-spec` | 澄清后的断言 |
| 将来上自动化时把规则型用例落成单测（**当前纯手工，先不做**） | `/tdd` | 标 `[规则型]` 的用例 |
| 回归时原问题仍在、根因不明 | `/diagnose-bug` | 复现步骤 + 日志 |
| 划影响面前要先知道到底改了哪些文件 | `/review` | 起点 commit / 分支 |

完整链路、三条交接接口、五对容易混的边界见 [`references/pipeline-map.md`](references/pipeline-map.md)。**`/qa-review` 和 `/review` 名字像、职责完全不同**，拿不准时先看那张边界表。

## 阶段间的门

只有两个硬门，其余都能并行：

- **澄清没过，不进用例**。两条并行判据：会改变预期结果的 `[待确认]` 项必须先确认；`[待确认]` 总数超过全部断言的三分之一时，整批不进用例阶段（见 `qa-clarify`）。只影响文案或非关键路径的，可以边写边确认，但要在用例里标出来。
- **冒烟没过，不转测**。冒烟用例有未通过项时，明确告诉用户"该模块不具备转测条件"，而不是"基本可用"。

其余情况——比如需求还在澄清但已能写核心正向用例——允许并行，别把流程走成串行阻塞。

## 收口

每个阶段结束时，把产出归位：用例进用例库、术语进术语表、Bug 模式进知识库。归位不是归档动作，是让下一轮少讲一遍。归位后告诉用户下次可以直接从哪个阶段开始。
