# 项目测试资产布局

`/qa-flow` 进场时按这份布局找资产，`/qa-cases` 按这份布局存放产出。**这是默认约定，不是强制**——项目已有自己的约定时，以项目为准，并把实际路径记下来。

## 默认布局

```
docs/qa/
├── glossary.md          术语与规则字典（唯一的词义来源）
├── knowledge/           业务知识库
│   ├── state-machines/  状态机模型（每模块一份）
│   ├── rules/           业务规则与字段规则
│   ├── exceptions/      典型异常场景库
│   └── releases.md      版本风险与遗留问题
└── cases/               用例库
    ├── <module>_业务流程测试用例_带数据与SQL.md
    ├── <module>_业务流程测试用例_带数据与SQL.xlsx
    ├── <module>_业务流程_冒烟测试.md
    └── <module>_业务流程_冒烟测试.xlsx

（<module>_专项测试用例.md/.xlsx 只在真做了专项时才有，默认不存在）
```

用例放 `docs/qa/cases/`，导出副本放同一层——**不要 md 在仓库、xlsx 在本地桌面**，两份分离三个月后必然对不上。

## 与 SDD 资产的边界

SDD 那套资产与测试资产在同一个仓库里并行，各占各的位置，不互相搬：

| 资产 | 位置 | 归谁 | 测试侧怎么用 |
| :--- | :--- | :--- | :--- |
| 领域语言 | `CONTEXT.md` | `/domain-modeling`、`/grill-with-docs` | 引用，不重定义（分工见下） |
| 决策记录 | `docs/adr/` | `/grill-with-docs` | 澄清时读，判断某条规则为什么长这样，别在用例里重新论证 |
| 特性工作区 | `.scratch/<feature>/`，spec 在 `specs/` | `/to-prd`、`/to-spec` | spec 的验收标准是用例输入，但 spec 本身不复制进 `docs/qa/` |
| 代码地形 | `docs/codemap/` | `/codemap` | 推影响面时查"这张表还有谁在读" |
| 业务验证 | `docs/qa/` | `/qa-*` | 本文件 |

`CONTEXT.md` 与 `glossary.md` 的分工容易糊：

- `CONTEXT.md` 是**词义的唯一真源**——这个词在业务上指什么
- `glossary.md` 记**词的落地映射**——它在系统里叫什么、落在哪个字段或页面、业务口语怎么叫

同一个词两处都出现时，词义以 `CONTEXT.md` 为准，字段与页面以 `glossary.md` 为准。项目没有 `CONTEXT.md` 时，`glossary.md` 第一列就兼任词义，不必为此专门建文件。

**铁律：`docs/qa/` 只放测试资产。** 把 PRD、spec 复制进来就产生了第二份真源，改一处漏一处，半年后没人知道哪份是准的。

## 路径登记

首次使用、且项目里没有 `docs/qa/` 时，问用户一次：

1. 资产放哪（项目内 `docs/qa/` / 其他本地目录 / Confluence 空间 / 禅道产品）
2. 记在哪——写进项目根 `AGENTS.md` 一行即可：

```
QA assets: docs/qa/            # 或 wiki: <space>/<page-id>、zentao: product=<name>
```

登记后不再重复问。路径失效（目录被移走）时，重新问一次并更新这一行，不要在旧路径上猜。

## 术语表格式

`glossary.md` 是 `/qa-cases` 用词与 `/qa-clarify` 判断层时的唯一词义来源。一个词只写一次。

| 术语 | 定义 | 别名/旧称 | 所属模块 | 来源 |
| :--- | :--- | :--- | :--- | :--- |

**术语** — 系统里实际出现的词，不用同义词替代。
**定义** — 一句话说清它指什么，不含流程描述。
**别名/旧称** — 业务口语、旧系统叫法。写用例时用标准词，括号里可带别名，方便业务方评审。
**来源** — 需求文档、字段名、还是业务方口述。来源是"口述"的要标 `[待确认]`。

术语表只收**有歧义风险的词**，不收全量字段字典。判断标准：两个人在评审时可能对它有不同理解的，才进表。

## 知识库三件套

每个模块沉淀三份，缺哪份就补哪份：

**状态机模型** — 状态清单 + 迁移表（从态、事件、条件、到态、触发者）。写清终态与不可达态。这是回归影响面推断的基础。

**业务规则与字段规则** — 编号的规则清单（如 `R-CONTRACT-03`：合同金额变更超过 10% 需重新审批）。规则要带条件和边界，不写"按规则处理"。

**典型异常场景库** — 踩过的坑，一条一行：现象、触发条件、根因分类、复现要点。这是新人上手和回归设计最有用的资产。

## 换项目时

换项目不等于复用旧资产，但骨架可以复用：

| 保留 | 重建 |
| :--- | :--- |
| `docs/qa/` 目录结构 | `glossary.md` 全部内容 |
| 用例模板、Bug 模板、分级标准 | `knowledge/` 下所有模块资产 |
| 六个跨模块检查点（见 `../../qa-cases/references/domain-chain.md`） | `cases/` 下所有用例 |

旧项目的资产**留在旧项目里**，不要搬进新项目再改——搬过来会带着旧术语污染新术语表，改到一半分不清哪个词是这个项目的意思。

新项目开工时，先跑一遍 `/qa-clarify` 把术语表从需求里长出来，比先建目录再填内容快。
