# 跨桶流水线地图

qa 桶不是旁支。测试与 `dev/`、`sdd/` 共用同一条交付链路，只在**产出物**上分工：dev 管代码怎么被正确写出来，qa 管业务怎么被验证过。这个文件说明两者在哪一步交接、交给谁、交什么。

各 skill 的细节不在这里重复，只留接口。

## 1. 三条入口，先判走哪条

| 入口 | 触发条件 | 走法 |
| :--- | :--- | :--- |
| **A｜有 PRD 或愿意先出 PRD** | 需求要留档、跨迭代、多人协作 | `/idea-to-prd`（从零）或 `/to-prd`（已有对话）→ `/to-spec` → `/tdd`，qa 在两端接 |
| **B｜口头需求、无 PRD、工期紧** | 缺产品经理、业务方只说了半句 | `/qa-clarify` 直接出断言，用它替代 PRD 里"验收标准"那一半 |
| **C｜需求简单且完整** | 单一功能面，目标、范围、完成行为都已说清，没有要 grill 才能定的开放问题 | `/to-spec` 直入（过 completeness-bar）→ 用例直接拿 spec 的验收标准 |

**B 不是降级，是按现状取最短路径。** 升级到 A 的信号只有三个：这需求要跨迭代、要给别人接手、要写进合同或验收单。没有这三个信号就别为了"规范"补一份没人看的 PRD。

**C 是 `/to-spec` 自己的第三扇门，测试侧要特别小心它。** 准入由 `completeness-bar` 两道判定：**Simple**（一个功能面，结论一两句说得完）+ **Complete**（目标、范围含进出、完成行为都已陈述，且没有 grill 才问得出的开放问题）。

问题在于：**这个 gate 是开发侧自评的，判的是"够不够拆 spec"，不是"业务上真的没洞"。** 少了 grill 和 PRD 两道缓冲，需求里的洞会直接固化进 spec，再顺着 spec 进代码——等到写用例才发现，返工成本已经是三倍。

所以走 C 的需求，`/qa-clarify` 的断言检查不能省，而且要用它反过来复核那两条 gate：**Simple 是不是真的只一个功能面、Complete 是不是真的没有未定的边界与异常**。发现洞要在 spec 落地前抛出来，不要等到 `/qa-cases` 阶段——那时候 spec 已经拆完，改的是实现而不是纸面。

## 2. 全链路

| 序 | 产出物 | 谁做 | 落到哪 |
| :--- | :--- | :--- | :--- |
| 1 | 需求共识 | `/grill-me`（无文档）或 `/grill-with-docs`（要留 ADR / 领域术语） | 对话；后者落 `CONTEXT.md` + `docs/adr/` |
| 2 | 可验证断言 + 疑问清单 | `/qa-clarify` | 清单交付业务方；断言进项目知识库 |
| 3 | PRD（走 A 时；走 B 用断言替代，走 C 跳过） | `/idea-to-prd` 或 `/to-prd` | `.scratch/<feature>/` |
| 4 | spec（原子、planning-complete；走 C 时由需求直拆，无 Parent） | `/to-spec` | `.scratch/<feature>/specs/` |
| 5 | 代码 + 单测（红绿重构；**团队暂无自动化时跳过**） | `/tdd` | 代码库 |
| 6 | 业务用例（smoke / full，含数据与 SQL） | `/qa-cases` | `docs/qa/cases/` |
| 7 | 代码审查（Standards + Spec 双轴） | `/review` | 审查报告 |
| 8 | 直接验证 + 关联回归清单 | `/qa-regress` | `docs/qa/cases/` |
| 9 | 验收结论 + 演示保障 + 复盘 | `/qa-review` | `docs/qa/knowledge/releases.md` |

5 与 6 可并行：开发在写代码，测试在写业务用例，不必等。

## 3. 三条硬接口

交接必须给具体东西，不能说"你接着弄"。

**接口一：断言 → spec 验收标准**
`/qa-clarify` 的每条断言（输入 + 规则 + 预期）直接就是 `/to-spec` 里 spec 的验收标准。反向也成立：spec 写完之后，它的验收标准是 `/qa-cases` 的输入之一，不是另写一套。两边措辞不一致时以断言为准——断言是对业务方确认过的。

**接口二：用例 → 单测（当前不启用）**
`/qa-cases` 里标 `[规则型]` 的用例（预期只依赖规则判定、不依赖页面观感）是将来接 `/tdd` 的候选。**团队目前纯手工测试，这条接口不要用**——不要因为标了就往 `/tdd` 塞，也不要在用例里写测试框架代码。等具备自动化能力后再启用，届时只需把 `[规则型]` 条目改写成单测，测试点不必重写。

顺带一条即使将来也成立：跨三个模块造数的业务链路用例，单测接不住，塞过去只会得到一堆 mock。

**接口三：diff → 影响面**
`/review` 产出的改动清单（改了哪些文件、哪些层）是 `/qa-regress` 推影响面第 1 层"同数据"的**依据**，比开发口头说的"就改了一点"可靠。没有 diff 时，regress 要如实说"影响面未确认"，不要凭模块名猜。

## 4. 五对容易混的边界

模型最容易在这五处走错，判定时先看这一列。

| 容易混 | 差别 | 怎么判 |
| :--- | :--- | :--- |
| `/grill-me` vs `/qa-clarify` | 对**人**拷问 vs 对**文档**找断层 | 业务方 / 研发在对话里能立刻回答 → grill；只有文档或人不在场 → clarify 出清单异步问 |
| `/to-spec` vs `/qa-cases` | 给**实现者**（怎么建）vs 给**执行者**（怎么验） | spec 是原子的、一个能独立实现；用例是穿过状态机的业务流程，会跨多个 spec |
| `/tdd` vs `/qa-cases` | **代码级**红绿 vs **业务级**人工 | 跑在 CI 里、断言函数返回值 → tdd；要登录、点按钮、查库、看通知 → cases |
| `/review` vs `/qa-review` | 看**代码 diff** vs 看**版本业务质量** | 问的是"这段代码写对了吗" → review；问的是"这版能不能上" → qa-review |
| `/diagnose-bug` vs `/qa-regress` | 找**根因**（不改代码）vs 划**范围**并验证 | 现象复现不了、不知道为什么会这样 → diagnose；知道改了哪、要确认没改坏别处 → regress |

`/qa-review` 与 `/review` 名字像，职责完全不同，两句都要看：review 是代码门，qa-review 是业务门，上线前两道都过才算完。

## 5. 外部系统落点

| 系统 | 在链路里的位置 | 谁调 |
| :--- | :--- | :--- |
| **Confluence** | 需求源（读页面 + 子页 + 附件）；疑问清单发布页（业务方在页面上回，比发 Word 强）；团队用 Wiki 管用例时作为用例归档处 | `confluence` skill |
| **禅道 story** | 需求源之一。`zentao-cli` 能读 product/project/story，需求写在 story 里时优先读它而不是听转述 | `zentao-cli` |
| **禅道 bug** | 回归验证的全生命周期：拉详情 / 评论 / 变更记录 → 回写结论 → 不通过另开单 | `zentao-cli` |
| **禅道用例** | **接不进**。`zentao-cli` 只覆盖 product/project/story/task/bug/todo，没有测试用例对象 | — |
| **`CONTEXT.md`** | 领域语言（业务词本身的意思）。`docs/qa/glossary.md` 记的是"业务词 → 系统里叫什么、落在哪个字段/页面"，引用 CONTEXT.md 而不重定义 | `/domain-modeling` |

## 6. 什么时候不该走这条线

单字段加减、纯文案、配置项开关、样式微调——直接给 5 条 smoke，验完收工。启动澄清 + 断言 + 全量用例属于过度动作，会挤掉真正需要覆盖的流程。

**判断标准**：这个改动有没有可能让某条业务流程走到一个没写过的状态？没有就跳过。
