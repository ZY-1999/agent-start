# 修复验证与回归

修复验证最容易犯的错，是只验原问题。原问题修好了、旁边被改坏了，一周后再炸一次——那不算修完。

## 1. 拿到三个东西

缺任何一个，先去拿，不要凭印象开始：

- **原复现步骤**——Bug 单里的，不是你现在回忆的
- **修复说明**——改了哪里，是改了数据、改了逻辑，还是改了状态判定
- **影响面声明**——开发认为还影响了什么；没有声明就由你在第 3 步自己推
- **改动清单**——实际动到哪些文件、哪一层。"就改了一点"不算依据；有起点 commit 或分支就用 `/review` 拿 diff，拿不到就明确标"改动范围未确认"

Bug 在禅道时用 `zentao-cli` 拉单子正文、评论、附件与变更记录。修复说明含糊（"已修复""调整了逻辑"）时，直接问改的是哪一层，不要猜。

**完成标准**：四样齐；修复说明能指到具体改动层。

## 2. 直接验证

用原复现步骤原样跑一遍，一步都不许省、不许"按道理应该过了"。

再补三条：

- **原问题的边界**：修复前失败的临界值，修完后再取一次等号与越界
- **修复方式的副作用**：如果改成"加限制"通过，就去验限制会不会挡住本该通过的正常场景
- **原路径的重复执行**：连续两次操作、返回再进入，确认不是只在首次生效

**完成标准**：原复现步骤跑通，且边界与重复执行两项都有结论。

## 3. 推影响面

按这三层推，每层给出**依据**，不要凭感觉列一堆无关模块：

| 层 | 怎么推 | 依据来源 |
| :--- | :--- | :--- |
| **同数据** | 改了哪个表/字段，还有谁读它 | 数据模型、SQL、页面字段来源 |
| **同状态机** | 改了哪个流转条件，同一状态的其他出口会不会受影响 | 状态机模型 / 业务知识库 |
| **同规则** | 改了哪条校验规则，还有谁引用这条规则 | 业务规则字典 |

三层之外，再看**下游联动**：这个模块的产出是不是别的模块的输入（见 [`../qa-cases/references/domain-chain.md`](../qa-cases/references/domain-chain.md)）。

推不出来时说实话："影响面未确认，建议开发补充改动清单"——比编一份看起来很全的清单更负责。

原问题复现不了、或者现象和修复说明对不上时，先 `/diagnose-bug` 把根因钉住再回来划范围。范围是在"确定改了什么"之上算出来的，根因没定就划范围等于瞎猜。

**完成标准**：每层都给出"受影响 / 不受影响 / 未知"，未知项有跟进动作。

## 4. 出回归清单

按 [`../qa-cases/references/case-template.md`](../qa-cases/references/case-template.md) 的回归表出清单，一行一个验证点，标明是**直接验证**还是**关联回归**。

关联回归不要展开成完整用例——写清验证点和判断标准即可，执行时再展开。展开会让清单长到没人跑。

**完成标准**：直接验证与关联回归分开列；每条有判断标准；未知项已标注。

## 5. 给结论

三种结论，只说一种，不要模糊：

- **通过**——原问题解决，影响面已验证，可关单
- **条件通过**——原问题解决，但影响面中某些项未验证（列出来，说明风险）
- **不通过**——原问题仍在，或修复引入新问题（附复现步骤）

**回归未通过的单子不许关**。发现新问题时，按 `references/bug-report.md` 另开一条，并在两条之间建立关联，不要塞在原来那条的评论里——塞进去的 Bug 会消失。

**完成标准**：结论明确到可以决定是否关单；不通过时有可直接复现的步骤。

## 6. 回写

把结果写回原单（禅道评论或用户指定位置），内容包含：验证了哪些、结论是什么、新开单的编号。然后提醒用户更新单子状态。

如果这次修复暴露了一个**可复用的检查点**（比如"凡改状态判定必须回归超时分支"），补进项目知识库 `docs/qa/knowledge/`，下次直接查。
