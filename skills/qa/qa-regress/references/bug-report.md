# 结构化 Bug 报告

研发无法复现、无法判断优先级的单子，等于没提。这份模板的目标是：**任何人拿到它，能独立复现、能独立判断该多快修**。

## 字段与写法

| 字段 | 必填 | 写法要求 |
| :--- | :--- | :--- |
| 标题 | 是 | `[模块] 现象` —— 一句话说清哪个功能出了什么偏差。不写"XX 有问题" |
| 严重等级 | 是 | 按 [`../../qa-review/references/severity.md`](../../qa-review/references/severity.md) 判定，不凭感觉 |
| 优先级 | 是 | 修复紧迫度，可与严重等级不同（严重但可下版修 = P2） |
| 复现环境 | 是 | 环境、版本号、账号角色、组织/项目范围 |
| 前置条件 | 是 | 数据状态。缺了这行，Bug 一半复现不了 |
| 复现步骤 | 是 | 编号动作，每步一个操作。含要输入的**具体值**，不写"输入合法数据" |
| 预期结果 | 是 | 按需求原文写，并注明需求出处（页面/文档章节） |
| 实际结果 | 是 | 客观描述观察到的现象，不写推测。有报错贴原文 |
| 影响范围 | 是 | 影响了哪些角色、哪些数据、是否已产生脏数据、会不会扩散 |
| 附件 | 视情况 | 截图（标出异常位置）、日志、请求响应、SQL 查询结果 |

## 标题写法

| 不行 | 可以 |
| :--- | :--- |
| 完工按钮点不了 | [派工单] 派工单已领用备件但未出库时，完工提交按钮不可点击 |
| 数据不对 | [合同] 合同金额变更后，合同列表页金额未同步，仍显示变更前值 |
| 审批有问题 | [返修单] 审批人离职后单据停留在审批中，无代理人也无超时转办 |

标题里带上**触发条件 + 现象**，研发扫列表就能分流。

## 反例与正例

**反例**

> 标题：派工单有问题
> 步骤：新建派工单，完工，报错
> 预期：应该能完工
> 实际：报错了

这条单子的问题：不知道哪个账号、哪张单、什么状态、报什么错。研发要花半小时问，最后可能还是复现不了。

**正例**

> **标题**：[派工单] 领用备件后未出库时提交完工，提示"备件未出库"但无跳转入口
>
> **严重等级**：严重 / **优先级**：高
> **环境**：测试环境 v2.3.1，账号 `svc_zhang`（服务工程师，华南区）
> **前置条件**：派工单 `PG20261019001`，状态=执行中(30)，已关联备件领用单 `LY20261019003`，领用单状态=已审批未出库
> **复现步骤**：
> 1. 用 `svc_zhang` 登录，进入「服务管理 → 派工单」
> 2. 打开 `PG20261019001`，点「完工提交」
> 3. 填写完工说明"更换主轴轴承"，点「确定」
>
> **预期结果**：按需求「派工单完工前须校验备件出库状态」允许提交并提示去出库，或阻断并给出出库入口
> **实际结果**：弹出提示"备件未出库"，点确定后关闭弹窗，页面无任何出库入口，无法继续
> **影响范围**：所有领用后才出库的派工单都无法完工；已在测试环境产生 3 张卡单（`PG...001/002/004`）
> **附件**：弹窗截图、接口响应 `POST /service/dispatch/finish → 500 {"code":"SPARE_NOT_OUT"}`

## 提交流程

发现 Bug 后：

1. **先查重**——同模块同现象是否已有单子，避免研发合并时漏掉你的补充信息
2. **建单**——禅道用 `zentao-cli` 创建，字段按上表填；类型选 `bug`，关联原需求（story/需求单）
3. **分配**——给到模块负责人，不是给到"开发组"
4. **补附件**——截图与日志在同一个动作里上传，不要"稍后补"

脏数据要单独说明：产生了多少条、在哪个库、能不能清理。研发修代码之后还要清数据，这一步不写进单子就会被忘掉。

## 关单前

修复验证未通过的 Bug **不许关单**（见 `/qa-regress`）。关单时补三样：

- 验证结论（哪条路径验过、什么结果）
- 修复方式简述（改了哪层，便于以后同类问题定位）
- 是否产生回归风险、关联了哪些新单
