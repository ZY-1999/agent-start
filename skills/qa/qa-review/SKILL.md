# 版本验收与质量复盘

这个 skill 只有一个任务：**让"能不能上"这个问题有明确答案**，而不是一句"基本没问题"。

**别和 `/review` 混。** `/review` 审的是代码 diff 是否符合仓库标准与原始 spec，产出审查报告；这里审的是版本能不能交付，产出验收结论。前者是代码门，后者是业务门，上线前两道都要过。`/review` 的结论可以当第 1 节的输入，但代替不了验收结论——代码全对、业务流程走不通的版本照样不能上。完整链路与另外四对边界见 [`../qa-flow/references/pipeline-map.md`](../qa-flow/references/pipeline-map.md)。

## 1. 汇总质量数据

四组数据，缺哪组就说哪组没数据，不要用感觉补：

| 组 | 内容 | 口径要求 |
| :--- | :--- | :--- |
| 覆盖率 | 已执行用例 / 计划用例 | 分模块列，不只给总分；**再按 L1/L2/L3 分层列**——L1 必须 100%，L2 只看 P0 是否跑完 |
| 通过率 | 通过 / 已执行 | **按场景算，不按步骤算**——一步错导致整条流程断，算一步通过会虚高 |
| 未解决 Bug | 按严重等级分组 | 每条给：阻塞与否 + 有无规避方案；分级口径见 [`references/severity.md`](references/severity.md) |
| 阻塞项 | 卡住验收的具体事 | 环境、数据、依赖系统、外部审批 |

数据来源依次找：用例库执行记录 → 禅道 Bug 列表（`zentao-cli` 查询）→ `/review` 的代码审查结论 → 用户口述。用口述数据时标注"用户口述，未经系统核对"。

**权限项单独列，不并进通过率。** "跨组织越权未通过"混进"整体通过率 95%"里就等于没了。内部业务系统没有外部攻击面，但**内部越权看数据就是事故**——权限用例任一不过，可直接判不可验收。

专项（L4）只在真做了的时候报。没做就在报告里写一句"本次未做专项测试（内部系统，无专项要求）"，不要写"性能：未测试"——那看起来像漏了，实际上是不需要。

**完成标准**：四组数据齐，或明确说明哪组缺失及其影响。

## 2. 给结论

三种结论，选一种，并给出理由：

- **可验收**——无阻塞项，未解决 Bug 均有规避方案或有明确的不影响范围
- **有条件验收**——有阻塞项但可降级（列出降级方案与代价）
- **不可验收**——存在阻塞级问题（列出具体项与责任方）

判断时守两条：

1. **P0 业务流程有未通过项 = 不可验收**，不论通过率多高。
2. 未解决 Bug 数量本身不是结论，"有没有落在核心业务链路上"才是。

不要为了配合工期把结论往上抬。说不清楚的地方写"无法判断，缺 XX 数据"，这比一个乐观结论安全。

**完成标准**：结论明确，每条理由可追溯到第 1 步的数据。

## 3. 演示保障

演示出问题和线上出问题是两件事——演示是**一次性、有人看、不能重来**的。

三件事必做：

1. **演示数据**：按演示路径逐条准备，覆盖核心业务链路的正向流程，提前跑一遍到终态。不现场造数。
2. **规避路径**：对有未解决 Bug 的模块，确认演示路径能不能绕开；绕不开就换路径，不是"到时候注意点"。
3. **兜底方案**：准备截图/录屏/预跑结果，出问题时能立刻切换，不在台上排查。

另外确认：演示账号权限、演示环境是否等于测试环境、是否有他人在同一环境操作（并发踩数据的经典死法）。

**完成标准**：三条路径都验证过一遍；兜底材料已就位。

## 4. 复盘

发布后做，聚焦可改的，不聚焦该怪的：

- **Bug 分布**：模块 / 类型 / 严重等级三维，找出集中区
- **根因分类**：需求模糊 / 设计缺陷 / 代码实现 / 测试覆盖不足 / 环境问题
- **效率**：平均修复时长、返工率（同一功能反复改的次数）
- **遗留风险**：带进下个版本的问题

关键一个数：**因需求模糊导致的理解偏差类 Bug 占比**。这个数直接指向 `/qa-clarify` 该不该加码——占比高说明澄清环节没拦住，下个迭代在澄清上多花两小时能省掉后面两天返工。

**完成标准**：四组分析有数；改进建议能落到具体动作（改哪个环节、谁做、下个版本验证什么），不是"加强沟通"。

## 5. 沉淀

三样东西回写，不然下次还是从零开始：

- 版本风险与遗留问题 → `docs/qa/knowledge/releases.md`
- 新发现的业务规则或状态机修正 → 对应模块的业务知识库
- 反复出现的问题模式 → 知识库的"常见问题与防呆检查点"

回写完告诉用户：下个版本可以直接复用哪几条，哪几条已经过期该删。知识库不收过期内容，收多了等于没收。
