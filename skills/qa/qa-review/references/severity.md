# 严重等级与验收门槛

`/qa-review` 判断"能不能上"，`/qa-regress` 给 Bug 定级，都按这份口径。用同一把尺子，避免"我的严重、你的次要"。

## 严重等级

| 等级 | 判定 | 典型表现 |
| :--- | :--- | :--- |
| **致命** | 核心业务流程中断，或产生不可逆的数据错误，且无规避方案 | 单据无法提交/审批、状态卡死无出口、金额或数量算错写入库、权限越权可见他人数据 |
| **严重** | 主流程可走但结果有偏差，或需要用户绕路才能完成 | 跨模块数据不一致、下游未联动、应触发的通知未发、有规避方案但业务方不接受 |
| **一般** | 非核心功能异常，或边界场景错误，有替代路径 | 列表排序错、筛选条件失效、非关键字段校验缺失 |
| **轻微** | 不影响业务判断的呈现问题 | 文案错别字、提示语不准确、样式错位、导入导出格式不美观 |

两条硬规则：

1. **产生脏数据的一律 ≥ 严重**，哪怕现象看起来轻微。脏数据要清理、要回溯、要通知业务方，成本远超代码修复。
2. **越权可见一律 ≥ 严重**，涉及数据的报致命。这不是体验问题。

## 优先级

优先级是**修复紧迫度**，不是严重程度。一个致命 Bug 如果已被规避且有降级方案，优先级可以不是 P0。

| 优先级 | 含义 | 判断 |
| :--- | :--- | :--- |
| **P0** | 本版本必须修 | 阻塞转测、阻塞验收、阻塞演示路径，或涉数据/合规 |
| **P1** | 本版本应修 | 不阻塞主链路，但业务方明确要求本版可用 |
| **P2** | 可下版本修 | 有规避方案，或影响面局限在少数场景 |

业务分层对应（制造业系统：业务正确性 > 交互体验 > 界面美观）：

| 分层 | 关注点 | 默认优先级 |
| :--- | :--- | :--- |
| P0 业务流程与边界 | 端到端流程、状态机流转、规则校验、异常分支 | P0–P1 |
| P1 交互与功能逻辑 | 控件联动、增删改查、权限、输入校验 | P1–P2 |
| P2 界面与易用性 | 视觉、适配、操作便捷 | P2 |

## 严重 × 影响面 → 优先级

| 严重等级 \ 影响面 | 全量用户 / 核心链路 | 部分角色 / 分支路径 | 少数场景 / 边缘 |
| :--- | :--- | :--- | :--- |
| 致命 | P0 | P0 | P1 |
| 严重 | P0 | P1 | P1 |
| 一般 | P1 | P2 | P2 |
| 轻微 | P2 | P2 | P2 |

表是默认值。下面三种情况可以往上提一档，但要在单子里写理由：

- 演示/验收路径正好落在这个点上
- 问题会随时间恶化（数据累积、越拖越难清）
- 同类问题已复发第二次以上

## 验收门槛

**不可验收**——命中任一条：

- 任一 P0 业务流程用例未通过
- 存在致命级未解决 Bug，且无规避方案
- 存在未清理的脏数据，且无法界定影响范围
- 核心链路上有阻塞项未关闭（环境、数据、外部依赖）

**有条件验收**——全部满足：

- 无致命级未解决项，或有规避方案且业务方书面接受
- 严重级未解决项均有规避方案，且已实测规避路径有效
- 脏数据已界定范围，清理方案已排期且不阻塞上线

**可验收**——无未解决 P0/P1，或剩余项均为一般/轻微且业务方接受带往下版本。

## 判定示例

| 现象 | 定级 | 理由 |
| :--- | :--- | :--- |
| 合同审批通过后，合同状态仍为"审批中"，下游无法生成订单 | 致命 / P0 | 核心链路中断，无出口 |
| 派工单完工后，完工记录生成 2 条重复数据 | 严重 / P0 | 产生脏数据，且随使用累积 |
| 服务工程师能看到其他区域的客户档案 | 严重以上 / P0 | 越权可见，涉数据合规 |
| 备件列表按金额排序不生效 | 一般 / P2 | 非核心功能，有替代路径（导出后排序） |
| 提示语"操作成功"应为"提交成功" | 轻微 / P2 | 不影响判断 |

拿不准时，往**高**定一级，并在单子里写清判断依据。定高了研发会来问，定低了没人来问——后者更危险。
