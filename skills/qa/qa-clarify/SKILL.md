# 需求澄清与补全

需求模糊不是"文档写得差"，是**没人把半句话补成一句可以判真假的话**。这个 skill 的产出是两组断言：能判真假的，和还不能判的。

## 1. 拿到原文，不做转述

先取需求原文，不要用用户的口头总结代替：

- Confluence 页 → `confluence` skill 读页面正文 + 子页 + 附件
- 禅道 story → `zentao-cli` 读需求单正文、评论与变更记录
- 本地文档 / 截图 → 直接读
- 只有口头描述 → 把用户的每句话原样记下来，作为"需求原文"，后续引用它而不是引用你的理解

**需求已经被 `/to-spec` 用 completeness-bar 放行（简单且完整，无 PRD）时，别把那个 gate 当成已确认。** 它判的是"够不够拆 spec"，不是"业务上没洞"。用这轮的断言复核它的两条：Simple（真的只一个功能面？）、Complete（边界、异常、数据形态真的都定了？）。洞要在 spec 落地前抛出来，落地后改的是实现，不是纸面。

原文缺失的分支就是缺口，转述会把缺口磨平，看起来什么都说了。

**人在场就先拷问，别急着出清单。** 需求方或研发此刻就在对话里能回答时，先用 `/grill-me` 把能当场问清的问完，再回来做断言——清单发出去通常要等一天，而工期没有一天。要沉淀 ADR 或领域术语还混乱时用 `/grill-with-docs`：它产出的 `CONTEXT.md` 是领域语言本体，`docs/qa/glossary.md` 记的是"业务词 → 系统里叫什么、落在哪个字段或页面"，**引用它，不重定义**。人不在场、或手上只有文档时，直接进第 2 步。

**完成标准**：手上有一份可逐句标注的原文，来源已记录；需求方可达的话，能当场问的已经问完。

## 2. 切成可验证断言

把原文逐句切成断言，一句一条。一条合格断言同时具备三件事：

- **输入**：谁、在什么状态下、做了什么
- **规则**：系统按什么判定（状态流转条件、额度限制、时间窗口、权限范围）
- **预期**：结果是什么，落在哪个字段 / 哪个页面 / 哪条通知上

缺任何一件，就是一条**断层**，进第 3 步。

**完成标准**：原文每一句都落到了某条断言上，没有"这句话大概是说……"这种悬空句。

## 3. 找五类断层

按这五类扫，每一类都有对应的追问角度：

| 断层 | 长什么样 | 怎么问 |
| :--- | :--- | :--- |
| **分支缺失** | 只写了顺利路径，没写驳回、撤回、超时、并发 | 这个动作失败了会怎样？谁重试？ |
| **状态未闭环** | 出现了新状态，但没说谁能改、能改成什么、终态是什么 | 这个状态还能不能退出？卡在这里多久算异常？ |
| **规则无边界** | "金额超过一定值要审批"——一定值是多少 | 边界值取等号吗？跨边界时已存在的单据怎么办 |
| **角色未定义** | 说"审批人审批"，没说审批人是哪个岗位、能不能代审、找不到人怎么办 | 这个人休假了走谁？换岗位后历史单据归谁 |
| **字段来源不明** | 页面要显示某值，但没说是实时算、快照存、还是从别的模块同步 | 上游改了，这里跟着变吗？ |

制造业系统的断层八成落在**状态机**和**跨模块数据流**上。跨模块的常见联动点见 [`../qa-cases/references/domain-chain.md`](../qa-cases/references/domain-chain.md)，扫断层前先过一遍那张链路表。

**完成标准**：五类各扫过一遍，每条断层都有具体位置（原文哪一句）和追问角度。

## 4. 标注，不隐藏

三种标记，一个都不能省：

- `[推断]` —— 你按行业惯例补的，写明依据（"按制造业返修惯例，返修单需在 7 日内闭环"）
- `[待确认]` —— 你补不出来、必须业务方回答的
- `[缺口]` —— 原文完全没有、但这类需求必然存在的（如：超时未处理怎么算）

推断要保守：**只补不会引起返工的部分**。凡是补错会导致用例和代码一起返工的，一律进 `[待确认]`，不要替业务方拍板。

**完成标准**：每条断层都有标记，`[推断]` 都带依据，`[待确认]` 都能对应到一个能回答它的人。

## 5. 出疑问清单

按 `references/question-list.md` 的表格出清单，一次交付给用户，并明确说：**这份清单要在开发动工前发给业务方或研发负责人确认**。

清单排序按"会不会让代码返工"降序——会改数据模型的排最前，纯文案的排最后。用户时间紧，最该先问的必须在第一屏。

业务方习惯用 Wiki 时，用 `confluence` skill 把清单发成页面、并在原需求页留一条链接。回帖就是答复，比在群里发 Word 更容易追溯谁在哪一条上拍过板。

**完成标准**：清单每条都有原文出处、建议答案、待确认人、状态列；已按返工风险排序。

## 6. 交接

澄清完不等于需求清楚了。明确告诉用户两件事：

1. 哪几条断言已经可以直接写用例（无 `[待确认]`）
2. 哪几条必须等确认才能写——这些是 `/qa-cases` 的阻塞项

然后交给 `/qa-cases`。`[待确认]` 项超过总断言三分之一时，不要进用例阶段，先催确认。

团队走 SDD 正线时，这同一份断言也直接作为 `/to-spec` 里 spec 的验收标准，**不要另写一套**。两边措辞不一致时以断言为准，因为断言是对业务方确认过的，而 spec 是转述。
