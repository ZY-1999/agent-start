# 用例表结构与产出规范

`/qa-cases` 的唯一表格真相源。四层用例各一张表，列不同是因为执行方式和受众不同。

## 冒烟表（L1）

| 序号 | 模块 | 测试点 | 操作步骤 | 预期结果 | 优先级 |
| :--- | :--- | :--- | :--- | :--- | :--- |

- **测试点** 一行一个，不超过一句
- 不写测试数据与 SQL（要能照着点 5 分钟跑完）
- **优先级** 只有 P0 / P1，不出现 P2、P3
- 总条数 5–15 条；超过 15 条说明混进了 L2

冒烟的唯一目的是回答"这个模块能不能转测"，所以每条都必须是**会阻断业务链路的**。校验文案、颜色、排序的，不进冒烟。

## 场景表（L2）

| 序号 | 业务场景 | 前置条件 | 操作步骤 | 预期结果 | 测试数据 | 校验 SQL | 预估(分) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

### 列的定义

**业务场景** — 一句话说清"谁在什么情况下做什么，要验什么"。写成"派工单完工提交"，不写成"验证完工功能"。

**前置条件** — 三件事写全，缺一件别人就复现不了：

1. 数据状态（已有未完工派工单 1 张，关联合同 X）
2. 操作角色（服务工程师，所属组织 = 华南）
3. 权限范围（可编辑本人派工单，不可见他人）

数据不是现成的，就补造数步骤或造数 SQL。写"已存在一条已审批合同"却不说怎么造，执行的人第一步就卡住。

**操作步骤** — 编号的可执行动作，每步一个动作。不写"检查 XX 是否正确"，那是预期结果。超过 12 步拆成两条。

**预期结果** — 必须可判真假，落到具体位置：

| 不要写 | 改写成 |
| :--- | :--- |
| 页面显示正确 | 状态栏显示"已完工"；完工时间 = 提交时间；不可再次编辑 |
| 流程正常 | 派工单状态 30→40；生成完工记录 1 条；触发 OA 通知给项目经理 |
| 数据保存成功 | `t_service_dispatch.status = 40`；`finish_time` 非空且 ≤ 当前时间 |

一条用例有多个预期结果时，分行写，不要挤在一格里。

**测试数据** — 造数用的关键字段值，只写会进入断言的部分：单号、状态初值、金额、时间、组织、角色账号。不写全表字段。

**校验 SQL** — 从数据库侧验证结果的语句。手工测试一样要查，光看页面看不出字段有没有落库。要求：

- 直接可执行，带 `WHERE` 精确到本次造的那条数据
- 查的是**断言用到的字段**，不是 `SELECT *`
- 字段归属不确定时先核对表结构，不要按命名猜（表结构说明见 `docs/qa/knowledge/`）
- 结果为空也是一种预期，写成注释说明"预期返回 0 行"

**预估(分)** — 手工执行这条大概几分钟。估不准就写区间（5–10）。这一列决定能不能排出工期，不要全填 5。

## 功能表（L3）

| 序号 | 功能点 | 前置条件 | 操作步骤 | 预期结果 | 测试数据 | 校验 SQL | 预估(分) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

和 L2 的差别只有第一列：**功能点**写的是单个功能，不是一条流程（"合同金额字段精度校验""订单列表按金额排序"）。

其余列的要求与 L2 完全一致。**不要因为它是 L3 就放松预期结果的标准**——"提示正确""排序正常"这类写法在 L3 里同样要返工。

L3 只收场景覆盖不到的东西：字段级校验、列表通用能力、单点状态操作。每条的"功能点"后面可以补半句为什么场景覆盖不到，方便评审时砍掉冗余项。

## 专项表（L4，默认不出）

**内部业务系统不做专项测试，这张表通常不存在。** 只有用户明确要求（客户要报告、上线前安全评审、要对外开放）或需求出现明确信号时才建。不要为了"齐全"先建一张空表。

建了才用下面的格式：

| 序号 | 类别 | 检查项 | 操作步骤 | 预期结果 | 判定依据 | 优先级 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |

**类别** — 性能 / 安全 / 兼容 / 联调，四选一，不要自造类别。

**检查项** — 从 `special-checks.md` 的扩展清单挑，不要凭空想。写成"导出 5 万行 Excel""A 账号改 URL 访问 B 的单据"。

**操作步骤** — 必须写清数据怎么造（1 万条怎么来）、账号怎么切、外部系统怎么模拟失败。这类用例最容易写成"验证性能是否可以""验证权限是否正确"，那样没人能执行。

**判定依据** — 可量化的观察方式：耗时秒表读数、SQL 查询结果、断网/停服务操作、浏览器控制台截图。不要写"感觉不卡"。

L4 通常不需要每行都配 SQL，"判定依据"填的是**什么算通过**：`首屏 ≤ 5s`、`返回 0 行`、`日志表有本次操作记录`。

**权限的功能验证在 L2/L3，不在这张表。** "改 URL 看别人的单""无权限按钮还能点""成本价谁都能看"是功能需求，写进业务用例。只有真做安全专项时，才在这里用另一种方式复核一遍——功能层是"按角色点界面"，专项层是"绕过前端直接调接口"，两者不重复，但也只在做专项时才需要后者。

## 执行清单

| 批次 | 内容 | 谁跑 | 预估 | 通过标准 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |

- 批次按**先跑会阻断后续的**排序：冒烟 → 主链路 → 分支与权限 → 功能细节（→ 专项，仅真做了才加）
- **谁跑**：开发自测 / 测试 / 运维 / 现场，写具体角色不写"相关人员"
- **预估**：累加对应用例的预估列，不要凭感觉
- 未执行的批次在交付时单独点名，不要含糊成"基本跑完了"

## 合并与单元格规则

同一业务流程的多条用例（前置条件与步骤相同，只有预期结果不同）：

- **A、B 两列（序号、业务场景）纵向合并单元格**，一个流程一行视觉块
- 预期结果、测试数据、SQL 分行，不合并
- 合并后该块的序号只出现在首行

这条规则的用意：评审时一眼看到一个流程，而不是看到五行看起来一样的步骤。

L3、L4 同样适用——同一功能点的多条校验合并，不要一条一重复。

## 双格式产出

Markdown 是正文（评审、diff、进 Git），`.xlsx` 是交付副本。两份必须同源生成，不要手改其中一份。

xlsx 生成要求：

- 首行冻结，列宽按内容自适应，预期结果列宽 ≥ 50
- 合并单元格按上面的规则处理
- 不合并数据行，不合并表头以外的横向单元格
- 一个文件多个层次时（L2 + L3），分 sheet，sheet 名用 `L2-场景` / `L3-功能`

## 文件命名（默认约定）

```
<模块>_业务流程_冒烟测试.md / .xlsx          # L1
<模块>_业务流程测试用例_带数据与SQL.md / .xlsx  # L2 + L3
<模块>_专项测试用例.md / .xlsx                # L4（默认没有这个文件）
```

## 回归表（供 `/qa-regress` 使用）

| 序号 | Bug ID | 类型 | 验证点 | 判断标准 | 结果 |
| :--- | :--- | :--- | :--- | :--- | :--- |

**类型** 只有两种：`直接验证`（原问题复现路径）、`关联回归`（影响面）。两者分开列，不要混排——混排会让人以为关联项也是必过项。

`结果` 填 通过 / 不通过 / 未执行。未执行的必须在交付时单独点名。
