# 测试用例产出

用例的价值不在条数，在于**执行的人愿不愿意跑、跑完能不能判断过没过**。开发内测流于形式，多半是因为用例写成了"自己去点点看"。

## 1. 定层次

用例分四层。不是四种文档，是同一份用例库里四类条目，深度和受众不同。**默认出 L1 + L2**，L3 跟需求复杂度走，**L4 默认不出**：

| 层 | 类型 | 作用 | 规模 | 默认 |
| :--- | :--- | :--- | :--- | :--- |
| **L1** | 冒烟 | 转测门槛：全过才具备转测条件 | 5–15 条 | 每次都出 |
| **L2** | 场景（业务流程端到端） | 主体：穿过状态机与模块边界 | 按模块规模 | 每次都出 |
| **L3** | 功能（单点正反与边界） | 补场景穿不到的细节 | 每个功能点 2–5 条 | 需求涉及才出 |
| **L4** | 专项（性能/安全/兼容/联调） | 只有明确要求时才做 | 按需 | **默认不出** |

优先级就是这个顺序：**冒烟 > 场景 > 功能 > 专项**。时间不够从下往上砍，**永远不砍 L1**。

**L4 默认不出，是因为现在的对象是内部业务系统**——使用者全是公司员工，不对外。这类系统不做专项测试是正常交付，不是遗漏。真正会出事的几类（跨组织看到别人的单、单据攒多了列表打不开、两人同时审批撞车）**属于功能正确性，在 L2/L3 里测**，见第 5 节。

从用户的话里判该出哪几层：

| 信号 | 出哪几层 |
| :--- | :--- |
| 转测、内测、冒烟、"最低标准""先能跑起来" | L1 |
| 业务流程、端到端、完整用例、带数据、要归档 | L1 + L2 |
| 这个模块要测全、给客户验收、要交测试报告 | L1 + L2 + L3 |
| 提到权限、"谁能看哪些数据"、角色隔离 | 上面几层 + **L2/L3 的权限场景**（不是 L4） |
| 明确说要性能测试 / 安全测评 / 兼容性报告 / 以对外为目标 | 上面几层 + 对应 L4 |
| 没说 | L1 + L2，并说明 L3 需要什么信息才展开；L4 默认不做 |

判不准时问一句"这次是给开发内测用，还是要进用例库"。**不要主动问"要不要性能和安全检查"**——内部系统问这句只会让人以为该做，然后做不实。

**完成标准**：层次已定，并已对用户说明本次出哪几层、不覆盖什么。

## 2. 手工执行的硬约束

团队没有自动化，全部由人照着跑。这决定三件事，写用例时不能违背：

1. **前置条件必须手工造得出来**——要么写清造数步骤（3 步以内），要么给造数 SQL。写"已存在一条已审批的合同"却不说怎么造，执行的人第一步就卡住。
2. **校验 SQL 不是可选项**——手工测试一样要查库确认状态码与字段落库。只看页面看不出"状态从 30 改成 40 了，但 `finish_time` 没写"。这是手工测试最容易漏的一层。唯一豁免是 L1 冒烟（要能照着点 5 分钟跑完，见 `references/case-template.md`）；L2/L3 无校验 SQL 视为未完成。
3. **单条用例步骤不超过 12 步**——超过就拆。手工会漏步，漏一步结论就不可信。

每条用例标注**预估执行时长（分钟）**，否则排不出工作量，也说不清"这批用例要测几天"。

## 3. 场景（L2）：按业务流程序列化

L2 是主体，**不按功能点罗列**（"字段 A 必填""按钮可点"），按业务流程序列化：一个场景从发起那一刻起，穿过所有状态，到终态为止。

```
发起 → 校验 → 审批/流转 → 状态变更 → 下游联动 → 终态
```

每个场景必须写清它**穿过的模块边界**——制造业系统的问题大多不在单个页面里，而在"上一环节的状态没传给下一环节"。跨模块联动点见 `references/domain-chain.md`。

场景要覆盖的是**分支**，不只是正向：驳回后重提、撤回、超时、并发操作、跨组织流转。只写顺利路径的场景，等于没测状态机。

**完成标准**：每条 L2 都能指出它在业务流程序列上的位置（上游是谁、下游是谁、终态是什么）。

## 4. 功能（L3）：只补场景走不到的

场景是一条流程从头走到尾，天然盖不住三类东西：

| 补什么 | 例子 |
| :--- | :--- |
| **字段级校验** | 必填 / 长度 / 格式 / 精度 / 特殊字符；同一字段在不同状态下能否编辑 |
| **列表通用能力** | 筛选组合、排序、分页跳页、导出当前页与导出全部、列显示配置 |
| **单点状态操作** | 启用停用、删除与恢复、批量选择、重复点击（幂等） |

写 L3 的规矩：每条要说清**为什么场景没覆盖到它**。说不出来，说明该并进 L2。

**L3 不是把每个字段列一遍。** 一个表单 30 个字段不等于 30 条用例，只挑有校验规则、有状态差异、有跨字段联动的。把没有规则的字段写进用例，执行时会变成"点点看"，反而拖垮内测。

**完成标准**：L3 每条都对应一个场景覆盖不到的具体风险点。

## 5. 专项（L4）：默认不出

**内部业务系统，无外部用户，无专项测试要求 → L4 不出。** 交接时说一句"本次不涉及专项测试"就够了。

不出 L4 不等于不管那几类风险。内部系统真正会出事的七件事，**归到功能层测，不单列专项文件**：

| 风险 | 落在哪层 |
| :--- | :--- |
| 跨组织/跨项目看到别人的单（改 URL 里的 id 试） | L2 权限场景 |
| 无权限的按钮还能点（再绕过前端调一次接口） | L3 权限 |
| 成本价 / 客户手机 / 银行账号全员可见，**导出文件里也可见** | L2 权限场景 |
| 单据攒到 1 万条后列表打不开 | L3 列表边界 |
| 提交连点 5 次生成 2 条单 | L3 单点操作 |
| 两人同时审批同一单，出现 2 条审批记录 | L2 异常分支 |
| 导出文件在 WPS/Office 打不开或乱码 | L3 列表能力 |

这七条不需要专项工具、不需要造压测环境，一个账号一条数据就能验。它们只是因为"内部系统嘛"容易被跳过——**跳过它们才是真的漏**。

### 什么时候才打开 L4

只有两种情况：

1. 用户明确要（客户要测试报告、上线前安全评审、系统要对外开放）
2. 需求里出现明确信号：要接入外部系统、要过安全合规、有现场设备要联调

要出的时候按 `references/special-checks.md` 的扩展清单取料，**挑中的才写**，没挑的写"不适用 + 理由"。清单里已按性能/安全/兼容/联调分好类。

**"基础"的边界要守住。** 写一份谁也执行不了的压测清单，比不写更糟——它会让人以为覆盖过了。

**完成标准**：L4 给出"出 / 不出"的明确结论；不出时已完成上面七条的归位，不留空档。

## 6. 写用例

结构照 `references/case-template.md`，四样缺一不可：

- **前置条件**：数据状态 + 角色 + 权限，写到别人能复现
- **操作步骤**：可执行的动作，不是"验证 XX 功能"
- **预期结果**：可判真假的观察点——落在哪个字段、哪个状态、哪条通知、哪张单据上
- **测试数据与校验 SQL**：造数用的关键字段值 + 查结果用的 SQL

预期结果写成"页面显示正确""流程正常"的，返工重写。判断标准很简单：**另一个人只看预期结果，能不能独立判断通过还是失败**。

预期结果只依赖**规则判定**（金额边界、状态流转条件、权限矩阵、重复提交拦截）的，标 `[规则型]`。这个标记的含义是"将来上自动化时最容易改写成单测"，**当前仍是手工执行**——团队没有自动化，不要因为标了就觉得它不用人跑，也不要在用例里写测试框架代码。

**完成标准**：四样都齐；随机抽三条，只看预期结果能判定真假。

## 7. 覆盖检查

写完先自查，不是写完就交。按层过：

| 维度 | 查什么 | 落在 |
| :--- | :--- | :--- |
| 正常流程 | 主链路从头到尾至少一条完整走通 | L2 |
| 边界 | 金额/数量/时间/条数的临界值，取等号与越界各一条 | L2 / L3 |
| 异常 | 驳回、撤回、超时、并发、重复提交 | L2 / L3 |
| 权限 | 每种角色的可见与可操作范围，含跨组织/跨项目 | L2 / L3 |
| 功能细节 | 字段校验、列表能力、单点操作 | L3 |
| 数据量 | 单据攒到万级后列表/导出还能不能用 | L3 |
| 专项 | 性能 / 安全 / 兼容 / 联调——默认"不出"，用户要求时才"出" | L4 |
| 回归 | 本次改动影响到的已有功能，列出而不是展开成用例 | 清单 |

优先级：**P0 业务流程与状态/边界 > P1 交互与权限 > P2 界面与易用 > P3 专项**。

P2 不进冒烟。**权限越权（P1）不过可直接阻断上线**——内部系统里越权看数据就是事故。P3 只在真做了专项时才存在，不阻断转测。

**完成标准**：八个维度都有结论（覆盖 / 不覆盖 / 不适用），"不覆盖"的写明理由。

## 8. 合并去重

同一业务流程的多条用例，前置条件与步骤相同的合并成一行，用不同预期结果分行——用户在表格里看到的是**一条流程一行**，不是同一段步骤重复五遍。合并规则与单元格处理见 `references/case-template.md`。

合并后条数下降是正常的，别为了凑数把一条拆成三条。手工执行的时代，条数多不等于覆盖好，只等于没人跑完。

**完成标准**：没有两条用例的前置条件与步骤完全相同。

## 9. 落格式与执行清单

文件拆分按受众走，不要全塞一个文件：

| 层 | 文件 | 为什么分开 |
| :--- | :--- | :--- |
| L1 | `<模块>_业务流程_冒烟测试.md` / `.xlsx` | 发给开发自测，必须短，混进全量就没人看 |
| L2 + L3 | `<模块>_业务流程测试用例_带数据与SQL.md` / `.xlsx` | 测试自己执行与归档，L3 放后半章 |
| L4 | `<模块>_专项测试用例.md` / `.xlsx` | 默认不做；做了才单独成文件，受众是安全/运维/现场 |

- 不写用例编号，用序号；编号由用例库（或 Wiki 用例页）生成——禅道没有用例对象，不要指望入库生成
- Markdown 是正文（评审、diff、进 Git），`.xlsx` 是交付副本，两份同源生成
- 存放位置按项目已有约定走（见 [`../qa-flow/references/project-layout.md`](../qa-flow/references/project-layout.md)），没有约定再问用户

**执行清单**：手工团队拿到的不能只有用例表，还得知道按什么顺序跑。照 `references/case-template.md` 的执行清单表出（列结构以模板为准），默认四批：

1. **冒烟** — L1 全量，开发自测，约 30 分钟，全过才转测
2. **主链路** — L2 的 P0，测试，约半天，全过
3. **分支与权限** — L2 的 P1，测试，约 1 天，允许 P2/P3 遗留；**权限项必过**
4. **功能细节** — L3，测试，约半天

只有真做了专项才加「5 专项 / L4 / 测试或运维 / 半天」——**没有就不要在清单里留一行空的**，留了会让人以为漏了什么。

排序原则只有一个：**先跑会阻断后续的**。冒烟不过，后面全白跑；主链路不过，分支测了也没意义。

**完成标准**：md 与 xlsx 双版本已生成；执行清单有批次、责任人和预估，总时长算得出来。

## 10. 交接

交给用户时只说四件事：

1. 这次出了哪几层，覆盖了哪些流程，哪些明确没覆盖——**顺带说一句"专项不涉及"**，把结论说全，别让人回头问
2. L1 的通过标准是什么（"这几条全过才具备转测条件"）
3. 哪几条依赖 `[待确认]` 项，确认后要回来改
4. 执行清单总时长——"这批跑完大概两个工作日"

不要逐条复述用例内容，用户会自己看表。

走 SDD 正线时，spec 里的验收标准如果和这里对不上，回来改用例而不是改 spec——用例是对业务方确认过的那一版。

用例执行中发现的问题按 `/qa-regress` 的 `../qa-regress/references/bug-report.md` 开单，别记在用例表的备注里——记在备注里的问题会消失。
