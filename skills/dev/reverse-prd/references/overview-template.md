# 总览层模板

`00-总览.md`（PRD-01）。这一层只索引**文档**——业务全景、哪个域写到哪、覆盖了多少、按什么顺序读，不放业务细节。

它不索引代码。代码地形、文件清单、调用链一律在 `docs/codemap/`；本文件对工程侧只留一行指路。

## 模板

````markdown
# [产品名] 逆向 PRD · 总览

> 文档编号：PRD-01 ｜ 版本：v1.0（2026-10-23，基于 dev@41e9ecd 系统现状整理）

## 文档信息

只写版本块里没有的信息——编号、版本都在版本块里，不要在这里重复。

| 项 | 内容 |
|---|---|
| 这个系统是干什么的 | 一句话业务定位，产品能直接拿去对齐口径 |
| 谁在用 | 主要角色清单（如「设计工程师、工艺工程师、产品配置管理员」） |
| 文档负责人 | 谁维护这套文档（不是原作者，是下次改动时找谁） |
| 评审人 | 业务负责人 / 技术负责人 / 测试负责人 |
| 关联文档 | 设计稿、接口文档、需求池、外部系统对接文档的链接 |
| 代码基线 | 后端 `dev@41e9ecd` / 前端 `dev@a1b2c3d`；只有一边时写明「仅后端，前端未提供，入口与文案未核实」 |
| 覆盖度 | 4 / 5 个业务域、23 / 31 个场景已建文档；未覆盖见 [A02](appendix/02-未覆盖模块.md) |
| 待确认 | 4 条，按影响面排序见 [A01](appendix/01-全局待确认问题.md) |

**范围外**：本期逆向不覆盖的部分，一句话交代清楚——如「历史归档数据迁移、已下线的旧版导入工具、运维部署流程」。产品据此判断哪些问题不该在这套文档里找答案。

## 业务全景

跨业务域的端到端主线，一段文字加一张手绘流程图即可。它回答「这个系统在业务上是怎么跑起来的」，也是场景拆分的依据。

```text
产品分类 →（建档）→ 产品系列 →（建 BOM 版本 / 配置策略）→ 产品配置 →（审批通过）→ 生成产品编码
                                                                    ↓
                                                          推送 TC / CAPP / ERP
```

标出跨域的关键交接点；单个域内部的流程写在模块 §3 的场景流程里，不在这里展开。

## 业务能力地图

域按**业务能力**切分，不按代码目录、不按接口前缀。菜单与页面是找边界的线索，落笔时用业务名。

| 域编号 | 业务能力 | 用户从哪里进入 | 场景数 | 文档 | 置信度 | 状态 |
|---|---|---|---|---|---|---|
| M01 | 系列管理 | 后台「系列管理」菜单 | 8 | [M01](modules/M01-系列管理.md) | 高 | 已完成 |
| M02 | 产品配置与编码 | 后台「产品配置」、审批待办 | 12 | [M02](modules/M02-产品配置与编码.md) | 中 | 进行中 |
| M03 | 属性管理 | 后台「属性配置」 | 6 | [M03](modules/M03-属性管理.md) | 高 | 已完成 |
| M04 | TC 同步 | 无独立入口，由各域操作触发 | 5 | — | — | 未覆盖，见 [A02](appendix/02-未覆盖模块.md) |

状态取值：`占位`（只有编号与能力名）/ `进行中` / `已完成` / `未覆盖`。

**场景清单不在总览里**，在各模块 §2 的场景地图。总览只记数量——把上百条场景抄进来，就是第二个真相。

## 建议阅读顺序

`00-总览` → `common/06-术语表` → `common/01-角色与权限` → `common/02-业务数据结构` → 按 M01→M0N 顺序读模块 → `appendix/01`。

先读术语与角色再看模块——老系统的用词往往和业务方口径不一致，不先对齐，模块文档读起来处处别扭。

待确认问题不在这里复述，一律看 [A01](appendix/01-全局待确认问题.md)——它按影响面排好序，本文件再抄一份就是第二个真相。
````
