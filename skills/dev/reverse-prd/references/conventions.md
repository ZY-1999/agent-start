# 约定（权威归属、语言、编号、溯源、版本）

多文档体系的失同步几乎都来自两件事：**同一信息写在两处**、**编号被复用**。这份文件是这两件事的防线。

## 1. 权威归属

一个信息只在一个地方有权威版本，其他位置只能引用。

| 内容 | 权威位置 | 模块文档里怎么写 |
|---|---|---|
| 角色定义、权限矩阵 | `common/01-角色与权限.md` | 只列本域涉及的角色与可见范围；场景级差异写在场景的「权限与可见性」 |
| 业务对象、属性、关系、生命周期 | `common/02-数据字典.md` | 只列"本域读写哪些业务对象的哪些属性"，链接到 C02 |
| 状态集合、合法流转 | `common/03-枚举与状态机.md` | 本域的状态机（含流转性质与业务后果）在模块 §4.2 展开 |
| 异常情况、用户提示、静默失败 | `common/04-错误码.md` | 场景内异常写在该场景的「异常与边界」，只列本场景的 |
| 外部系统、时效、自动执行动作 | `common/05-非功能需求.md` | **不设模块级非功能节**；只有改变某场景行为的约束才写成该场景的规则或异常 |
| 业务术语、同义词冲突 | `common/06-术语表.md` | 直接使用术语，不重复解释 |
| **场景内规则** | 该场景的 §3.x.3 | 只写本场景的规则；两个以上场景共用的移到 §4.1 |
| **跨场景规则** | 模块 §4.1（`G<模块>-R<n>`） | 全系统共用的再上移到 `common/` |
| 业务断言与代码位置的对应 | `appendix/03-溯源台账.md` | 正文**不写**任何代码位置；台账里加一行 |
| 代码地形、文件清单、调用链 | `docs/codemap/`（项目图 + 每模块一份 feature 图） | 不引用、不复制；台账顶部指向本模块 CodeMap 一次 |
| 物理表结构（DDL） | `common/07-表结构DDL.sql`（实现侧，非产品文档） | 模块不复制；业务口径见 C02，映射对照见 A03 §3/§4 |
| 接口字段级结构 | `interfaces/M<模块号>-接口结构.md`（实现侧，非产品文档） | 业务口径在模块 §6 业务要素表；物理字段只出现在结构文件与 A03 |
| 待确认问题 | 各文档自己的 `待确认` 节 | 模块内写全并挂关联场景，A01 只做聚合与排序 |

跨模块规则（如"付款成功后订单状态变更"）写在**发起方模块**；被影响方写一句"由支付的付款结果驱动，见 M03 §3.x"，不重复描述过程。

规则只有三层：**场景内**（S 前缀）→ **跨场景**（G 前缀）→ **全局**（C 层）。同一条规则只能出现在一层，出现第二层就是重复。

PRD 目录里**不设**代码索引类文档（文件清单、扫描命令、目录树、模块-文件对照表）。这类内容一旦落进 PRD，就会和 `docs/codemap/` 形成两份互相漂移的索引。

## 2. 语言契约

**正文零实现。** 判断标准、禁用清单、白名单与四类改写对照，全部以 [business-voice](./business-voice.md) 为准——本文件不重复列，重复列就是第二个真相。

## 3. 编号

| 对象 | 格式 | 示例 |
|---|---|---|
| 总览 | `PRD-01` | — |
| 全局文档 | `PRD-C` + 两位序号 | `PRD-C03` |
| 模块文档 | `PRD-M` + 两位序号 | `PRD-M02` |
| 附录 | `PRD-A` + 两位序号 | `PRD-A01` |
| 模块（业务域） | `M` + 两位序号 | `M02` |
| 业务场景 | `S` + 模块号 + 序号 | `S02-01` |
| 场景内规则 | 场景编号 + `-R` + 序号 | `S02-01-R1` |
| 场景内功能点 | 场景编号 + `-F` + 序号 | `S02-01-F1` |
| 场景内异常 | 场景编号 + `-E` + 序号 | `S02-01-E1` |
| 跨场景规则 | `G` + 模块号 + `-R` + 序号 | `G02-R1` |
| 验收标准 | `AC-` + 场景编号 + `-` + 序号 / `F<n>` / `E<n>` | `AC-S02-01-1`、`AC-S02-01-F1` |
| 待确认 | `Q-M` / `Q-C` / `Q-A` + 编号 + 序号 | `Q-M02-1`、`Q-C01-1` |

四条硬约束：

- **编号只增不重用。** 场景或规则下线时标 `[已废弃]` 并注明对应文档版本，不删除、不把编号让给新内容——验收标准与待确认条目都靠编号回指。
- **一切挂在场景下。** 规则、功能点、异常、验收标准的编号都以场景编号为前缀，读者从一个 `AC-S02-01-F1` 能直接定位到哪个场景的哪个功能点。功能点 `F` 编号挂在场景流程（§3.x.2）的对应步骤行上，不单列一节。两个以上场景共用的规则升为 `G`，全系统共用的再升到 `common/`——只升不复制。
- **验收标准分两层。** 场景级 `AC-<场景>-<n>` 验端到端走通与后置结果；功能点/异常级 `AC-<场景>-F<n>` / `-E<n>` 验单个动作。一条只验一个可判定结果，写不成可判定结果的回规则表补规则。
- **编号不等于顺序。** 新增场景用新号，不为了阅读顺序重排旧号。

## 4. 文件命名

文件名与内容主体语言保持一致：内容是中文，文件名就用中文（`01-角色与权限.md`、`M02-订单.md`）——不出现"英文文件名 + 中文内容"的混搭。

- **编号前缀保留**：`00-`、`01-`、`M02-` 等排序前缀照旧，前缀之后的部分用内容主体语言。
- **目录名不改**：`common/`、`modules/`、`interfaces/`、`appendix/` 是结构角色而非内容，保持英文。
- 文件名只用中文、数字、连字符；不用空格和特殊字符。

## 5. 引用与溯源

- 跨文档链接用**相对文档的路径 + 锚点**：`[C01](../common/01-角色与权限.md#3-全局权限矩阵)`。锚点写之前先确认目标标题存在；标题改了要同步改锚点，否则链接静默失效。
- 模块文档只允许**引用**全局文档，不允许复制全局表格。
- **代码位置与物理名只出现在三处**：`interfaces/` 接口结构文件、`common/07-表结构DDL.sql`、`appendix/03-溯源台账.md`。路径相对仓库根，形如 `src/services/order.service.ts#createOrder`；非代码工件（DDL、配置）定位到文件即可。业务叙述正文（场景、规则、验收、C01–C06 业务表）一律不出现。
- **前端后端都在范围时，路径必须带仓库前缀**：`后端: src/.../AaadaaServiceImpl.java#save`、`前端: src/pages/series/index.tsx#SeriesForm`。两边目录常重名，不带前缀的路径半年后没人能定位。
- 正文断言与台账条目一一对应；台账缺行等于这条断言没有依据，复核时按缺陷处理。

## 6. 置信度

三分类，**模块头部标一次**，代表本域整体的把握程度：

- `高` —— 系统当前确实这样运行，有直接可核对的依据（代码、DDL、配置、测试、实际数据）；
- `中` —— 从系统行为推断，路径完整但业务意图未经确认；
- `低` —— 无法确认，规则可能不在系统里（在配置、外部系统或人的约定里）。

某条规则或某个场景把握低于模块整体时，在该条文本末尾内联标注 `（推断）` / `（未确认）`，不另设一列——一列里九成是「高」，反而没人看。

`低` 不允许只标了事：必须同步开 Q 条目，由人工确认或探针用例验证。猜测不许写成事实——理由见 [business-voice §六](./business-voice.md)。

## 7. 版本

每份文档的 H1 下一行必须有版本块：

```markdown
> 文档编号：PRD-M02 ｜ 版本：v1.0（2026-10-23，基于 dev@41e9ecd 系统现状整理）
```

前端后端都在范围时，两边的基线都要记，缺哪边就写明「仅后端」：

```markdown
> 文档编号：PRD-M02 ｜ 版本：v1.0（2026-10-23，基于 后端 dev@41e9ecd / 前端 dev@a1b2c3d 整理）
> 文档编号：PRD-M02 ｜ 版本：v1.0（2026-10-23，基于 后端 dev@41e9ecd 整理；前端未提供，入口与文案未核实）
```

模块文档再加一行定位信息：

```markdown
> 上级总览：[00-总览](../00-总览.md) ｜ 置信度：中
```

规则：

- 编号在文档创建时确定，之后不变；拆分子模块时新编号顺延（`M02` 拆出 `M06`、`M07`），不复用旧号。
- 内容变更升 minor（`v1.1`）；错字、链接、格式修正升 patch（`v1.0.1`）。
- **任一仓库的代码版本变化都要动版本号**：有实质内容改动时按内容变更升 minor；仅版本块变化（重扫后确认内容无实质变更）升 patch——读者靠版本判断文档描述的是哪一版系统。两侧基线只升一侧时，版本块里写清哪侧动了。
- 版本块里的 `基于 <分支>@<短 hash>` 必须是真实存在的 commit，不能用占位符蒙混。
- **不设变更记录。** 版本块是唯一的时间锚点，历史演进交给 git。文档只描述当前系统状态，不写"上一版是什么"。
