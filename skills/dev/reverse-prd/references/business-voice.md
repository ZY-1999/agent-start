# 业务语言契约（正文零实现）

这份文件决定 `docs/reverse-prd/` 能不能被产品读下去。核心一句话：**正文只写业务怎么运转，不写系统怎么实现。**

逆向 PRD 的材料来自代码，但成品不是代码的说明书。代码是**证据**，不是**内容**。核对过程留在写作过程中与 `appendix/03-溯源台账.md` 里，正文一个字都不带。

## 一、判断标准

每写完一段，问三个问题，任一答"否"就重写：

1. 产品经理读完这段，能拿去做需求决策、写验收、或者回答业务方提问吗？
2. 这段话里的每个名词，业务方在需求评审会上说得出口吗？
3. 把实现换掉（重写、换框架、换表结构），这段话还成立吗？

## 二、禁用清单

正文（`modules/`、`common/`、`00-总览` 的业务叙述部分）**禁止出现**：

> 边界：禁用清单约束的是**业务叙述正文**（场景、规则、验收、C01–C06 的业务表）。物理名允许出现在三处**实现侧交付物**——`interfaces/` 接口结构文件、`common/07-表结构DDL.sql`、`appendix/03-溯源台账.md`——它们自成一体（代码块 / SQL），不混入业务叙述；一旦混入，同样算泄漏。

| 类别 | 例子 | 为什么不行 |
|---|---|---|
| 表名、列名、字段物理名 | `aaadaa`、`adaa084='T'`、`aiaa004a` | 产品不认识；混淆码尤其致命 |
| 类名、方法名、文件名 | `AaadaaServiceImpl#save`、`AcaeaaMapper.xml` | 读者定位不到，也不需要定位 |
| 端点编号当功能名 | 「`aaadaa005` 新建」 | 编号不是业务动作，是接口编号 |
| 注解、框架、生成器 | `@Transactional`、`@Lock4j`、`JNPF 模板 16 动作` | 框架是团队内部事实，不是产品事实 |
| 消息码、异常类 | `i002`、`OngoalException`、`w101` | 用户看到的是文案，不是码 |
| HTTP 状态、Result 包装 | 「HTTP 200 + 业务码」「`Result.success()`」 | 联调细节 |
| 配置 key、缓存 key、队列名 | `tc.tcSyncProduct`、`MCMS:18:<code>` | 运维细节 |
| SQL 条件、查询实现 | 「wrapper 恒假」「`abaa084='F'`」 | 这是缺陷描述的实现版本，应写成业务现象 |
| 日志文案 | `log.warn`、`log.error` | 排查手段，不是行为 |
| 实现维度术语 | 事务边界、锁、幂等、补偿、降级、幂等标记 | 换成业务后果（见第四节） |
| 代码统计 | 「19 端点」「621 表列」「grep 命中 16 处」 | 代码规模不是产品事实 |
| CodeMap 链接、代码地形 | `[M02](../../codemap/M02-订单.md)` | 工程侧产物，产品文档不挂 |

## 三、允许出现的技术名词（白名单）

只有这些可以留在正文，且必须带业务说明：

| 允许 | 写法要求 | 例 |
|---|---|---|
| 外部系统名 | 首次出现给全称，后续用简称 | TC（Teamcenter）、CAPP、ERP（T100） |
| 接口标识 | 必须配业务名，路径只作标识 | 「系列列表查询（`POST /aaadaa/aaadaa002`）」 |
| 业务对象与属性 | 用业务名；物理名进台账 | 「系列编号」而非 `adaa006` |
| 单位、币种、编码规则 | 业务口径 | 「编码 8 位，前 2 位为系列代号」 |
| 产品内既有的行业术语 | 收进 C06 术语表 | 「部套」「DA 码」「全量 BOM」 |

## 四、四类高危内容的改写法

### 1. 删除标记 → 业务后果

```text
❌ 删除为逻辑删：adaa084='T'；已删记录不可再改/删（抛 i002）
✅ 删除后数据仍保留在库中，只是不再出现在列表与选择项里；
   已删除的记录不能再修改，也不能重复删除，重复删除会提示「该数据不存在或已被删除」。
```

### 2. 事务 / 锁 / 幂等 / 补偿 → 业务连续性

| 实现维度 | 要回答的业务问题 | 写法示例 |
|---|---|---|
| 事务边界 | 一次操作中途失败，业务上留下什么？全生效、全不生效，还是部分生效？ | 「保存系列时，主档与属性清单要么一起成功，要么都不落库；但推送给 TC 的动作不在其中，失败不影响本地保存。」 |
| 锁与并发 | 两个人同时改同一条数据会怎样？ | 「同一系列被两人同时保存时，后保存的覆盖先保存的，系统不提示冲突。」 |
| 幂等 | 同一个操作提交两次会怎样？ | 「重复提交返回同一张单据，不会产生两笔。」 |
| 补偿与降级 | 外部系统失败后，业务怎么补？ | 「TC 推送失败时本地照常保存，系列列表会出现『未同步』标记，需在『补充同步』里手工重推；系统不会自动重试。」 |

判断标准：这段话说的是**业务人员要处理的局面**，还是**开发人员要处理的异常**？前者留，后者删。

### 3. 错误码表 → 业务异常清单

```text
❌ | i002 | 主键为 null（update/delete 首行守卫） | AcabaaServiceImpl#update | 代码不可见 |
✅ | 修改/删除时记录不存在或已被删除 | 提示「该数据不存在或已被删除」 | 修改、删除、批量操作 | 操作不生效，数据不变 |
```

只保留三列产品用得上的：**什么情况 → 用户看到什么 → 业务后果**。用户看不到的码不写。

### 4. 功能清单 → 场景 + 操作清单

```text
❌ | F01-01 | 系列标准维护套件（查询/详情/保存/修改/删除/树/导出/复制/作废 + 6 个空壳端点） | POST /aaadaa/aaadaa001~016 |
✅ 场景 S01-01「新建系列并同步到设计系统」：
   前置：已建好产品分类；操作：填写系列信息 → 选择属性 → 保存 → 系统自动推送分类到 TC/CAPP；
   结果：系列可被 BOM 版本与产品引用；异常：TC 失败不阻断保存，列表标记未同步。
```

功能清单可以留，但它是场景的**索引**，不是主干：一行一个业务动作，动作名用业务动词（新建、作废、导出），不用端点编号。

## 五、文案与验收标准的写法

正文里只有两类文字必须**一字不差**，其余都可以概括：

| 内容 | 要求 |
|---|---|
| 用户看到的提示 | 照抄原文（含标点）。改写成"更通顺的说法"会让测试验错、让产品审错 |
| 验收标准 | 给定…当…则…，一条一个可判定结果。写不成这种句式，说明规则还没想清 |

**提示文案先从前端取**——页面上的字、i18n 里对应的值，抄原文即可。前端也拿不到时才写「文案由平台统一维护，当前不可见」并开 Q，**不要编一句像样的文案**：编出来的文案会被人当需求基线抄进前端。

用户故事只写一句：作为【角色】，我希望【做什么】，以便【得到什么价值】。它不承载规则，规则归场景的规则表。

**场景流程的步骤用业务要素与业务动作描述**：输入写「商品、数量、收货地址」，不写参数名；处理写「校验库存与限购 → 计算金额」，不写"调用库存服务"。判断标准还是那句——换掉实现，这段还成立吗？

## 六、写不出来怎么办

业务语言写不出来，通常不是语言问题，是三种情况之一：

| 症状 | 真相 | 处理 |
|---|---|---|
| 只能照着代码逐行翻译 | 没搞清这段代码对应的业务动作 | 回到菜单、页面、单据去找业务语境；找不到就在 §7 开 Q |
| 不知道这个字段业务上叫什么 | 字段无注释、无界面标签 | 用「待确认字段」占位 + 开 Q，不要用物理名凑数 |
| 这段行为本身就说不通 | 可能是缺陷 | 写成「当前表现为…，与业务预期不符」并开 Q，不要替它编理由 |

**不要为了让文档好看而编业务含义。** 一条编出来的业务规则比一个诚实的问号危害大得多——问号会被人回答，假事实会被当成需求基线。
