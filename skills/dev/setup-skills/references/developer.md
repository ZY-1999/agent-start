# 开发规范（Developer）

本仓库的编码与文档规范，人类与 AI 同样适用。动手改代码或规则资产前先读这一份。

## 一、通用编码与文档规范

### 命名

- 名字说明"是什么"，不说明"怎么实现的"；避免只有作者懂的缩写。
- 布尔量用肯定式（`isValid`、`enabled`），不用 `notXxx` 双重否定。
- 同一概念在代码、文档、issue 里用同一个词；换词等于换概念。

### 异常与日志

- 捕获异常必须输出日志并带上下文（哪个操作、哪个参数、哪个 id），禁止静默吞掉。
- 不为了"让流程继续"而 catch 后忽略；确实要降级，就写清降级到什么程度。
- 日志不打印密钥、token、完整证件号与客户隐私字段。

### 数据访问

- 避免循环内访问数据库或远程接口；需要多次查时先一次查出转 map，再在循环里取。
- 列表查询不传过滤条件时默认返回空结果集（或拼接恒 false 条件），由显式开关（如 `showAll`）放开。
- 更新前先查、再赋值、最后写回，不允许凭前端入参直接覆盖整行。

### 输入与边界

- 对外入口（Controller / 命令参数 / 文件解析）必须校验入参与长度、类型、范围。
- 集合判空用工具类（如 `CollectionUtils.isEmpty`），不手写 `size() == 0`。
- 金额、时间、数量使用明确类型与单位，不靠命名猜。

### 文档

- 注释解释"为什么"，不复述代码"做了什么"。
- 改了行为就同步改文档；文档与代码冲突时以代码为准并当场修文档。

### 红线

- 禁止在代码、注释、日志、测试数据中出现真实密钥与客户数据。
- 禁止执行 `rm -rf`、`DROP`、`git push --force` 等破坏性命令。
- 禁止自动 push，必须人工确认。
- 不主动改动 `.gitignore`；提交与暂存忠实遵守仓库现有忽略规则。

### 提交前

- 改动必须实际验证（编译、启动、跑一遍目标路径），验证不通过不提交。
- 仓库无自动化测试时不强行补测试框架，但要说明手工验证做了什么。

## 二、Skill 与规则资产规范

适用于承载 skill、prompt、agent 规则文件的仓库；不涉及这类资产的仓库，整节删除。

### 目录与命名

- 一个 skill 一个目录，目录名即 skill 名（kebab-case）。
- 入口固定 `SKILL.md`；细则拆到同目录 `references/`，最多一层，不再套子目录。

### frontmatter

- `name` 与目录名一致。
- `description` 写"什么时候该用我"，含用户会说的触发词；不写"我内部做了什么"。

### 渐进披露

- `SKILL.md` 只放决策点与流程骨架；长清单、格式模板、完整示例放 `references/`。
- `SKILL.md` 明显过长（约 500 行以上）就该拆；拆出来的内容要能被单独读懂。

### 指令写法

- 用祈使句写动作，不写"你可以考虑…"这类无约束表述。
- 每个可判定步骤给出可验证的完成条件。
- 明确"何时必须停下来问用户"，以及停下来要问哪几件事。

### 多平台清单与版本

- 改 skill 内容要同步各平台清单（plugin / marketplace 清单）与版本号，漏一处等于该平台拿到旧内容。
- 版本号遵循 semver：新增或改变行为升 minor，纯修正升 patch。
- 改了 skill 结构要同步代码地形地图，避免下次探索拿到过期索引。
