什么是 AI Coding？
从代码补全到 Agent 开发：能力边界、典型场景与工程实践

AI Coding 正在从个人开发者的效率工具演变为软件工程的基础设施。但"AI 能写代码"本身并不构成一个完整的技术判断——关键在于生成的代码能否通过审查、进入生产环境，并持续维护。本文沿"是什么、能干什么、不能干什么、怎么用好"四个问题展开。

一、是什么：定义、演进与定位

1.1 定义与能力范围

AI Coding 的工作方式是：模型根据开发者提供的输入约束——上下文代码、自然语言描述或结构化规格——生成代码或辅助完成编码任务。从能力范围看，它覆盖代码补全与续写、函数级代码生成、页面与组件搭建、API 接口实现、测试用例生成，以及架构设计辅助和需求到代码的转化。不同工具在这些能力层级上的覆盖深度差异显著。

判断一个 AI Coding 工具是否达到可用标准，核心不是看它能否生成代码，而是看它生成的代码是否具备三个属性：可控性、可审查性、可维护性。可控性指生成结果确定、可复现；可审查性指每段代码能追溯需求来源、能被逐条核对；可维护性指代码进入项目后，后续的同事敢于也便于改动。这三个属性决定了 AI 编码成果能否从实验环境进入生产环境，后文的所有结论都围绕它们展开。

1.2 三个技术阶段

按 AI 参与的深度划分，AI Coding 经历了三个阶段。每个阶段在输入方式、输出可控性和适用场景上有本质区别：

阶段代表模式输入方式输出可控性适用场景
第一阶段：代码补全 GitHub Copilot、Codeium 等补全工具 编辑器实时上下文 低，逐行建议由人采纳 日常编码提速、样板代码
第二阶段：对话式生成 ChatGPT、Claude、GLM 等通用模型 自然语言提示词 中，依赖 Prompt 质量与上下文完整度 方案设计、排障、原型验证、文档
第三阶段：Agent 与规格约束 Cursor、Claude Code、Devin 类 Agent 任务描述 + 仓库访问 中高，需逐项审查与测试门禁 任务级开发、批量重构

三个阶段是叠加关系而非替代关系，就像企业可以按场景混用：个人日常编码用补全，方案与排障用对话式，任务级开发在审查与测试门禁就绪后交给 Agent。行业多项开发者调研显示，仅补全类工具就能将日常编码效率提升 20%–40%；后两个阶段在特定任务上的增益更高，对应的质量把关要求也更高。

第一阶段：代码补全

补全工具通过分析编辑器当前上下文，预测开发者接下来要输入的代码，提供行级或函数级建议。它的核心价值是减少重复性编码：样板代码、API 调用模板、正则表达式、测试框架脚手架。局限同样明确：只能处理局部上下文，无法理解整体业务逻辑；产出需要开发者自行审查和整合；不具备需求理解和架构设计能力。它是有效的辅助工具，但不能独立承担开发任务。

第二阶段：对话式生成（Vibe Coding）

对话式工具将 AI 的参与范围从"代码片段"扩展到"功能模块"：开发者用自然语言描述意图，AI 生成完整的代码文件或方案。这类模式在排障、学习、方案对比、内部工具原型上表现出色，也是目前多数工程师的日常用法。但把它直接用于生产环境的核心系统，会遇到三个结构性挑战：

  1. 生成不确定性：相同的提示词在不同时间可能产出结构不同的代码，难以保证一致性。
  2. 审查困难：从提示词到代码之间缺乏可追溯链路，审查者无法验证 AI 是否正确理解了业务意图。
  3. 协作缺失：缺乏统一的需求规格，多人协作时容易出现风格冲突和接口不一致。

这三个挑战决定了对话式生成适合原型验证和探索性开发，而不适合直接承担生产级交付。

第三阶段：Agent 与规格约束

Agent 类工具在对话式的基础上增加了仓库访问、多文件改动、测试执行与自我修正的能力，可以承接任务级的开发工作。与此同时，行业正在探索另一条提升可控性的路线——Spec 驱动开发（SDD）：在生成之前，先将需求结构化为正式的规格文档，再以规格约束生成行为，使每段代码都能追溯到对应的需求条目，消除提示词驱动的不确定性。这条路线目前主要由平台级产品落地；个人开发者可以用简化方式获得类似收益——先让 AI 输出实现方案，人工确认后再让它按方案实现，同样能显著降低返工。

两种模式在关键维度上的差异：

维度对话式生成Agent + 规格约束
需求输入自然语言提示词任务描述 + 结构化方案 / 规格
生成确定性低，受上下文与表述影响较高，规格作为生成基准
代码审查黑盒，需逐行通读规格到代码可追溯，可逐项核对
多人协作弱，缺乏统一基准强，方案 / 规格作为协作基准
适用场景原型、探索、辅助分析任务级开发、批量重构

1.3 对工程师意味着什么

技术演进层面之外，工程师更关心的是自己的位置。AI Coding 不是第一次改变"写代码"这个动作的成本结构，每一轮生产力工具变革都伴随过同样的焦虑，而身处其中的工程师每一次都完成了过渡：

变革当时的主流疑虑后来的事实
汇编 → 高级语言编译器生成的代码性能不可接受手写汇编退出日常开发，懂底层的工程师反而更稀缺
手写代码 → IDE 补全 / 重构自动补全打断思路，重构工具不可信离开 IDE 重构工具的现代开发流程已不可想象
检索式查资料 → 对话式问答复制粘贴已足够好用正在发生，本文的主题

三轮变革的共同规律是：工具消灭的是重复劳动，不是使用工具的人。真正需要担心的不是被 AI 取代，而是被更早完成过渡的同行拉开效率差距。

同时也要明确三件 AI 目前做不了、也不该由它做的事：

  • 不承担架构决策。选 MySQL 还是 MongoDB、单体还是微服务——AI 能输出对比分析，但拍板依据是团队、预算与历史包袱，这些信息不在它的上下文里。
  • 不掌握业务理解。"为什么财务模块每月 15 号必须锁账"这类知识藏在组织流程与人的经验中，不在任何训练语料里，必须由工程师翻译给 AI。
  • 不承担线上责任。AI 可以给排查建议，但对故障报告负责的是提交代码的工程师，责任无法外包给工具。

对三个阶段的工具，一个统一且足够准确的心智模型是：

把 AI 当成"一个反应快、知识面广、但产出需要 Code Review 的初级同事"。

这个模型的三个特征，分别对应三条使用纪律：

特征具体表现使用纪律
反应快秒级产出完整代码，全天候响应不用"快"作为采纳依据，产出速度与正确性无关
知识面广主流语言、框架、运维脚本均有积累冷门场景要求它给出处，给不出就要警惕
需要 Review大方向正确，但会编造 API、遗漏边界、风格漂移一切产出过编译、测试、Review 三道关，与人写的代码同一标准

与这个"同事"协作的方式，本质上就是工程师做了十几年的事情：给任务、给上下文、验收产出、Review 代码。转移的是习惯，不是能力。

边界提示

业务解释是"最合理的推测"，不是事实；技术判断是语言事实，可以直接对照验证。业务结论必须找业务方确认——AI 是理解遗留代码的助手，不是业务历史的记录者。

任务定义：JDK 8 升 17、Date 全家桶换新 API、慢 SQL 优化、语言迁移。工作量不小但极其琐碎，属于典型的"模式已知"任务。

演示 B：慢 SQL 优化。输入表结构、慢查询与 EXPLAIN 结果，AI 的标准产出包含三部分：性能问题点清单（函数包列导致索引失效、SELECT * 阻断覆盖索引、子查询执行计划差）、改写后的 SQL 及每处改动原理、建议索引及列顺序依据。

这类任务 AI 表现稳定的原因具有普遍意义：迁移和优化是模式已知、语料充足的任务——无数工程师做过 JDK 8→11→17，标准解法遍布训练语料。AI 最擅长的正是此类工作。

实践建议

让 AI 在输出中附"变更点清单"（原写法 → 新写法 → 原因），把审查从通读全文变为逐项核对，这是迁移类任务的安全措施。SQL 索引建议必须在生产级数据量上实测验证。

三、不能干什么：能力边界

只讲好处的介绍是推销，讲清边界的介绍才是工程。本章五条边界，每条附现象与对策——这一章是建立信任的关键。

边界一：幻觉——编造不存在的东西

现象：AI 会以确定的语气输出不存在的 API、过时的用法、想象中的配置项。这不是故障，是大语言模型工作原理的固有属性——它计算的是"最合理的下一个词"，而不是"真实的下一个词"。这也是五条边界中最高频的一条。

对策：三条纪律。第一，生成代码必须通过编译与类型检查，这一关能挡住绝大多数幻觉；第二，不确定的 API 要求它给出处；第三，依赖坐标必须完整写进构建文件并在本地解析成功。

边界二：上下文限制——大项目全局理解不足

现象：模型只能看到输入给它的内容。大项目几十万行代码远超上下文窗口，典型症状有三：

  1. 重复建设：新生成的类与项目已有工具类功能重复——它不知道你们已经有一个 DateUtils。
  2. 破坏隐含约定：改 A 文件时违反 B 文件的口头约定（"这个 map 的 key 必须小写"），这类约定不在任何文件里。
  3. 长程遗忘：跨 20 个文件的重构，进行到后半段偏离前半段的设计。

对策：主动提供相关上下文（依赖类、接口定义、编码规范）；大重构拆成小步，每步可编译可回滚；优先使用能在仓库内自主检索的 Agent 类工具——它能缓解但无法根治这个问题。

边界三：安全合规——代码外发与审计

红线问题，引入前必须明确

  • 代码外发风险：贴给公网模型的每一段代码都离开了公司边界。密钥、内网拓扑、客户数据、核心算法，一条都不应出现在 Prompt 中。
  • 许可证风险：生成代码可能与开源代码高度相似，GPL 类许可证的传染性风险需经法务评估。
  • 合规路线：有合规要求的团队优先选择私有化部署模型（如 GLM 系列开源版）或提供数据不留存承诺的企业版工具。先与安全部门确认，再引入工具。

边界四：责任归属——提交者对代码负全责

提交 MR 的人是你，点 approve 的人是你，on-call 的也是你。"是 AI 生成的"在任何组织都不构成免责理由。

这条边界决定了 AI 时代的技能结构变化方向：写代码的量下降，读代码和做判断的量上升。代码审查能力从"入职培训内容"变成"职业生存技能"——这是第四章的出发点。

边界五：什么时候效率反而更低

以下场景中，"把需求说清楚"的成本高于"动手做"的成本，AI 的介入是负增益：

场景为什么帮倒忙更好的做法
一行小改动描述需求的时间比手改还长直接改
强业务逻辑上下文都在你脑子里，写 Prompt 等于口述需求文档自己写，让 AI 补测试
性能敏感代码AI 生成"平均值正确"的代码，不理解你的热点路径人写核心路径，AI 做基准测试脚手架
团队强规范生成 → 改风格 → 改命名，来回拉扯把规范文件作为上下文提供后再生成

判断标准与 2.0 节一致："说清需求的成本"对比"动手做的成本"，谁低用谁。承认 AI 有负增益场景，是用好它的前提。

四、怎么用好：六项实践

前两章回答"它能做什么、不能做什么"，本章回答"你该怎么做"。第一项是根基——给足上下文：对话级的 Prompt 写作与项目级的规则文件是一件事的两面，前者每次委托时交代，后者一次写好、长期生效；随后三项是对话级习惯，每个对应一个可以立即开始练习的动作；最后两项是项目级基础设施——维护地图、拷问需求——让团队与 Agent 的协作收敛而不是发散。

实践一：给足上下文——Prompt 写作与项目规则

Prompt 的本质是需求文档：你写给外包团队的需求文档怎么写，Prompt 就怎么写。同一个"实现分页"的需求，两种写法的产出质量差距巨大。反例：

没有技术栈，它猜一个；没有字段定义，它编字段；没有规范约束，风格随缘。结果能用，但要大改。正例：

技术栈、字段、返回结构、参照物齐备，一次生成的可用率显著提高。归纳成三要素：上下文（什么技术、什么场景）、约束（不能做什么、按什么规范）、示例（照着项目里哪个类写）。三要素齐备，一句"帮我写个 XX"才能变成一次合格的委托。

三要素里最花成本的是上下文与示例——每个 Prompt 都重新交代一遍，很快没人坚持。最常见的失误正在这里：Agent 每次进场都从零开始，不知道构建命令、不了解分层约定、不清楚哪些目录碰不得。解法是把可复用的部分沉淀成项目规则文件——在仓库根部放一份规则文件（AGENTS.md、CLAUDE.md、CONTEXT.md，各工具叫法不同，作用一致），把三件事写清楚：

  • 怎么构建与验证——构建、测试、lint 命令；这是 Agent 自查的依据，而不是靠它猜
  • 代码写成什么样——分层与命名约定、错误码风格，各给一个参照类；一个现成的类比十句描述管用
  • 什么不能碰——安全红线、合规要求、禁改目录、密钥与数据的处理边界

没有这份文件，同一个 Prompt 每次产出的风格都不一样；有了它，三要素中的上下文与约束由项目兜底，产出天然向项目规范收敛，Review 的纠偏成本大幅下降。

三件事是最小集，成熟形态会长成 Demo 08 的样子：规则文件不堆长文，而是索引到 docs/agents/ 下的分文件约定。

实践二：任务分解——拆到 AI 能处理的小块

"把订单模块重构成 DDD 风格"——这个任务 AI 处理不了。"把 OrderService 里的校验逻辑抽到独立的 OrderValidator 类，保持行为不变，先给出类骨架"——这个它一次就能做好。任务粒度的分界线：每一步产出可验证、可回滚。

这套拆法与带新人拆任务的方法论完全一致——你已经会了，需要的只是习惯的迁移。

实践三：代码审查——AI 是加速器，人是质量守门员

效率提升的前提是质量不坍塌。以下检查项建议直接纳入团队规范：

  • 编译 / 类型检查通过——挡住绝大多数幻觉
  • 单元测试通过且断言有效——警惕"永真断言"式测试
  • 没有编造的依赖和 API——构建文件坐标真实可解析
  • 边界与异常路径——null、空集合、并发、超时
  • 安全——SQL 注入、XSS、敏感信息入日志
  • 风格与项目一致——命名、分层、错误码

一个值得注意的事实：用好 AI 之后，工程师的代码阅读量是上升的，不是下降的——写得更少，读得更多，角色从生产者向审校者偏移。这恰好是资深工程师的优势区。

实践四：迭代修正——不指望一次生成完美代码

新手期待一次成活，熟练使用者都是多轮逼近：

两个立即可用的技巧：提供参照物——项目里一个现成的类，胜过十句描述；要求自我检查——"检查上面代码的边界情况并逐条列出"，AI 经常能挑出自己的毛病。

以上对话级实践对应的能力——写需求文档、拆任务、审代码、迭代地带人——都是工程师已经掌握的，需要的只是习惯的迁移。接下来两项则要在项目层面一次性建设。

实践五：用 CodeMap 给 Agent 指路

真实仓库动辄上千个文件，让 Agent 自己全仓搜索，既慢又容易断错调用链。给高频功能维护面向 Agent 的代码地图（CodeMap）——注意，不是给人看的架构百科。四条要领：

  • 路由，不是复述——地图不复制代码，只标注"去哪看、按什么顺序看、看什么证据"；省的是 Agent 的注意力，不只是 token
  • 渐进披露——第一屏只有入口与模块索引，细节等任务需要时再展开
  • 诚实标注不确定性——关键链路标 confirmed（已验证）/ inferred（推测）/ unknown（未确认），让 Agent 明确知道哪些不能信
  • 自带验证入口——每张图写清"用什么测试、命令、日志证明行为"，地图直接喂验收

两头都要用起来：开工先读图——需求、排障、迁移都从地图指路的位置进入，而不是从全局搜索开始；收尾做比对（drift-check）——拿 diff 与地图核对，入口、调用链、依赖等地形若被本次改动波及，以代码为准更新地图，过期的地图比没有地图更危险。地图本身也按需生成——新仓库不必预先铺图，首批代码落地后再生成项目级地图，之后增量维护；Demo 08 把这条约定连同 drift-check 的触发时机写进了 AGENTS.md。

实践六：需求从拷问开始（grill-with-docs）

「帮我做个分页」是最低效的开局——需求里的模糊点会全部变成 Agent 的自由发挥。更有价值的做法是先用拷问式访谈（grill-with-docs）把需求压实在：一次只问一个问题，顺着依赖逐个解决，每个问题给出推荐答案，能靠代码和地图回答的不开会空谈。访谈过程顺手沉淀两类资产：

  • 术语表（一页即可）：把"退款""撤销""部分退款"这类易混词的团队定义写下来；用语与术语表冲突时当场指出——多数争论其实是定义之争
  • ADR（决策记录）：只给满足三个条件的决策立档——难以逆转、未来读者会困惑"为什么这么做"、是真实权衡的结果

拷问结束后，你得到的是一份被压测过的需求说明、更新过的术语与决策，再交给 Agent 执行——此时 Prompt 里的每句话都有出处。

两类资产按需惰性创建：仓库里还没有它们时，Agent 静默继续，等术语或决策真正落定才落盘——预先铺满的文档没人维护，很快变成新的遗留代码。配套的纪律是冲突显式化：Agent 的输出与术语表或既有 ADR 矛盾时，必须显式指出（"与 ADR-0007 矛盾——但值得重开，因为……"），而不是静默覆盖。Demo 08 把这套约定写在 docs/agents/domain.md。

把实践一沉淀的规则文件、实践五的代码地图、实践六的拷问访谈连起来，就是 Demo 08 配置下一次任务的完整生命周期。注意两个人机交接点（Gate）——需求与规格的批准都由人拍板，Agent 只在批准后动手：
