# Demo 03：重构与迁移（JDK 8 → 17 + 慢 SQL 优化）

> 对应讲义章节：[2.3 场景三：重构与迁移](../../index.html#s2-3)

## 目标

展示 AI 在**模式已知、语料充足**任务上的统治力：JDK 升级改写、慢 SQL 优化。这类任务工作量不小但极其琐碎，是 AI 提效最明显的场景之一。

包含两个子演示：

- **A. JDK 8 → 17 迁移**（`jdk-migration/`）
- **B. 慢 SQL 优化**（`sql/`）

## 传统方式 vs AI 方式

| | 传统方式 | AI 方式 |
|---|----------|---------|
| JDK 迁移 | 逐个文件查 API 对照表、Google 迁移方案，一个工具类半天 | 贴代码 30 秒出改写 + 每处改动的原因说明 |
| SQL 优化 | 老师傅带 + 经验试错 | 贴建表语句 + SQL + EXPLAIN，出改写方案和索引建议 |

## 子演示 A：JDK 8 → 17 迁移

### 演示步骤

1. 打开 `jdk-migration/before/DateUtils.java`——典型的老工具类：`Date` + `Calendar` + `SimpleDateFormat` + 匿名内部类
2. 用下方 Prompt 让 AI 迁移
3. 对照 `jdk-migration/after/DateUtils.java` 展示：代码量减半、线程安全、行为对照表

### 推荐 Prompt

```text
把下面这个 JDK 8 风格的工具类迁移到 Java 17，要求：

1. Date/Calendar/SimpleDateFormat 全部替换为 java.time API
2. 匿名内部类 Comparator 替换为 lambda / Comparator.comparing
3. 用 text block 改写拼接的多行字符串（如果有）
4. 保持所有公开方法签名和行为不变（时区语义按系统默认）
5. 输出格式：完整迁移后代码 + 变更点清单表（原写法 → 新写法 → 原因）

[粘贴 DateUtils.java 代码]
```

### 讲解要点

- **"为什么 AI 做这个特别强"**：JDK 8→17 迁移是全网写烂了的主题，模式完全已知——引出"AI 擅长有标准答案模式的任务"
- **"注意我要求了什么"**：保持签名不变、行为不变、输出变更清单——这些约束让它不敢自由发挥
- **人的工作**：跑一遍既有单元测试。AI 改写 + 人验证测试 = 迁移速度翻几倍

## 子演示 B：慢 SQL 优化

### 演示步骤

1. 打开 `sql/before/slow-query.sql`——一个真实感十足的慢查询：`SELECT *` + 子查询 IN + 函数包列
2. 用下方 Prompt
3. 对照 `sql/after/optimized.sql` 讲解 AI 给出的三层产出：改写 SQL / 索引建议 / EXPLAIN 解读

### 推荐 Prompt

```text
MySQL 8.0，订单表 3000 万行，下面这条 SQL 跑了 8 秒，帮我优化：

[粘贴 slow-query.sql 中的 SQL]

建表语句和相关索引如下：
[粘贴建表语句]

EXPLAIN 结果：
[粘贴 EXPLAIN 输出]

要求：
1. 先指出当前 SQL 的性能问题点（逐条）
2. 给出改写后的 SQL，并解释每处改动的原理
3. 给出建议的索引（含列顺序），说明为什么这样排序
4. 提醒改写后可能改变语义的地方（如 NULL 处理、去重行为）
```

### 讲解要点

- AI 指出的典型问题：`IN 子查询` 执行计划差、`SELECT *` 无法覆盖索引、`DATE(created_at)` 函数包列导致索引失效
- **强调第 4 条约束**：让 AI 主动交代"语义可能变化的地方"——这是把 Review 清单前置到生成阶段
- 提醒：**索引建议必须自己在真实数据量上验证**，AI 给的是"最合理假设"，不是"你的环境的真相"

## 失误预案

- AI 改写悄悄改变了时区语义 → 好素材："看，这就是为什么要求输出变更清单"
- SQL 方案在你的库上没变快 → 讲第三章：性能敏感场景 AI 只提供候选方案，benchmark 由人跑
