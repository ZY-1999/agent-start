# Demo 05：写测试（补覆盖率 + 生成边界用例）

> 对应讲义章节：[2.5 场景五：写测试](../../index.html#s2-5)

## 目标

给一个计价函数补测试。重点不是 AI 会写 `@Test` 骨架，而是它**能想到人懒得想的边界**：临界值、精度、非法输入——并且顺手发现代码里的防御缺失。

## 传统方式 vs AI 方式

| | 传统方式 | AI 方式 |
|---|----------|---------|
| 耗时 | 1 小时（大部分人选择不写） | 1 分钟生成 + 10 分钟核对断言 |
| 用例设计 | 想到哪写到哪，边界靠心情 | 系统化：正常值 → 临界值 → 非法值 → 精度 |
| 额外收益 | 无 | 顺便指出被测代码的 bug（本例：负数数量没校验） |

## 演示步骤

1. 打开 `legacy/PriceCalculator.java`——只有 15 行的业务代码，规则一眼能懂
2. 提问现场："你们给这个函数会写几个测试用例？"（通常回答 2~3 个：正常、VIP、满 100）
3. 贴给 AI，用下方 Prompt
4. 对照 `ai-output/PriceCalculatorTest.java`，数一数 AI 给了多少个用例——**通常是人类现场说的 2~3 倍**
5. 重点展示它对"负数数量"和"精度"的处理，以及最后那段"代码问题提示"

## 推荐 Prompt

```text
为下面的计价函数写 JUnit 5 单元测试，要求：

1. 用 @ParameterizedTest 覆盖等价类和边界值（尤其注意折扣临界数量 99/100/101）
2. 必须覆盖：数量 0、负数、null 单价、超大数量（int 溢出风险）
3. 金额断言必须用 BigDecimal.compareTo，禁止用 equals（解释为什么）
4. 测试命名用中文 @DisplayName 说明业务含义
5. 最后回答：这段代码本身有没有防御缺失或 bug？

[粘贴 PriceCalculator.java]
```

## 讲解要点

- **"注意第 2 条 Prompt"**：我把"必须覆盖负数、null、溢出"写进去了——边界清单本身也是 Prompt 的一部分，这是"给约束"的示范
- **"AI 会发现代码的 bug"**：负数数量当前会返回负数总额（等于"下单越多退钱越多"），AI 在测试之外会主动指出——**测试 + Review 二合一**
- **"为什么禁止 equals 断言"**：`new BigDecimal("100.00").equals(new BigDecimal("100.0"))` 是 false（scale 不同），这是 Java 面试经典题，AI 能把这种细节写进测试
- **人是断言的最终审查者**：AI 生成的期望值要抽查手算，防止它"为了测试绿而写错期望值"（永真断言的变体）

## 与其他 Demo 的联动

- 本 Demo 的计价函数与 Demo 02 的 `double` 金额问题呼应：可以现场让 AI 把它迁移成 `BigDecimal` 版本（回到 Demo 03 的迁移能力）

## 失误预案

- AI 写了永真断言（如 `assertNotNull(result)` 了事）→ 现场教学："这就是第四章'代码审查'清单里'警惕无效断言'的含义"，追问让它改成具体值断言
- AI 忘记 `@ParameterizedTest` 依赖 → 讲幻觉问题：依赖坐标要让它写全
